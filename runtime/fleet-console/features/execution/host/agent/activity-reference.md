# Terminal 활동 상태 참조

OSC title, hook, Chat SDK job ledger 또는 PTY/Chat 전환을 수정할 때 읽는다. 상태의 권위·수명주기·실패 처리 근거를 보존한다.

- Agent activity has one authority per axis: the agent CLI's OSC terminal title decides whether the model is working, input-waiting hooks decide the awaiting state that titles cannot distinguish from idle, hook turn state is only the fallback for an unrecognized title, and the authority for background-pending work that outlives the turn is per surface: the live background-task list carried on the turn-stop and subagent-stop hook payloads for the PTY surface, and the session's own live job ledger for the Chat surface, which needs no hook because its SDK stream carries every task start and end for as long as the session lives. That list is applied as an absolute value, never as a spawn/stop tally: one workflow tool call fires a single spawn but one stop per workflow agent, so any counter drains while the workflow is still running. A stopping subagent is still listed as live in its own payload and must be excluded by its agent id, and that exclusion has to be remembered for the rest of the session: a named agent stays resident and listed as running after its work is done, so a payload alone can never tell resident from busy, and re-reading it as live work would wedge the operation out of idle and awaiting. The remembered ids are pruned by the next fully readable list that no longer carries them. Only agent work stands on this axis — subagents, named teammates, and workflows — because what a person waits on is the agent doing their work, not a command it left behind: a background shell a finished subagent started stays listed on the parent, and an MCP monitor task is resident for the life of the session, so counting either wedges the operation out of idle and blocks idle dormancy. A task type on neither list, and a task record carrying no type at all, is not proof that no work remains, so it stays opinionless like an unreadable list. Turn end carries its own report inside the turn-state signal rather than through a second hook on the same event, because hooks sharing an event run in parallel and a turn end that lands alone reads as a false idle for that frame — a spurious turn-ended notification and an idle arrival. Background-pending must never claim the working axis; it only prevents a false idle and blocks idle dormancy while set. On the hook-fed PTY surface it decays after a bounded TTL because hook delivery is best-effort — a lost stop hook must never wedge the badge on forever. The Chat surface carries no such shelf life, because its ledger is the session stream itself and is always swept when the session goes away, and a deadline there would quietly idle work that is still running. Everything that surface leaves undecided is therefore permanent, so it must decide: an unrecognized task kind does not stand on the axis there, a resident agent still listed after its end event is remembered and excluded exactly as the hook payload's is, and a list row that omits the kind never overwrites a kind already known. The title says that something is working, never whose work it is, so a title still working after turn end is read as the pending background work rather than as a running turn, and running wins only while a turn is in flight. Its working vocabulary is a glyph alphabet the CLI restyles between releases, so it is matched by family and several families stay matched at once. An unrecognized title, and a background report whose task list cannot be read, must stay opinionless so vocabulary drift degrades to the prior state instead of a false idle.

- The activity axis is one set of fields with two adapters, never one set per surface: the PTY adapter fills them from the OSC title and hooks, the Chat adapter from SDK turn boundaries and its live job ledger, and `chatActive` records only which adapter owns the axis. A chat-adopted session keeps no live PTY status — both chat-born and restored Operations sit at `dormant` — so `chatActive`, never `status`, gates a write to that axis from the Chat side; the PTY setters' lifecycle guard exists to drop hooks landing after teardown and silently discards every Chat report if reused there. Adding a parallel per-surface field splits one concept into two names and forces every reader to choose between them. Switching adapters clears what the previous one left, because a stale value is read as the new surface's first frame.
