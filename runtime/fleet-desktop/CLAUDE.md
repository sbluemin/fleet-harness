# Fleet Console Desktop

`runtime/fleet-desktop` is the optional thin Electron shell for Fleet Console.

## Directory index

| Directory | Responsibility |
|---|---|
| `src/` | Native app, window, menu, tray, and dialog lifecycle |
| `src/runtime/` | Managed Node and Console procurement and supervision |
| `assets/entry/` | Passive bootstrap status surface |
| `scripts/`, `build/` | Packaging and release policy |
| `tests/` | Shell, ownership, packaging, and runtime contracts |

## Constraints

- The Console product remains the sole server, PTY, provider, plugin, durable-state, and React owner. Desktop production source imports the shared `@fleet-console/protocol/desktop` contract; never Console internals. Packaged integration tests remain anchored to the published `@dotobokuri/fleet-console/desktop-protocol` compatibility surface.
- Startup launches the managed Console and hands the single window to its `/console/`. Desktop offers no surface for choosing, adding, or naming a Console — that belongs to the Console product, and a second copy of it here would split the list a user sees.
- The main process shows a Console only after verifying its identity. Before opening a remote origin, it confirms the live certificate against the fingerprint held by the local Console over a separate socket, then pins the credential-bearing connection. Console document URLs and fragments remain credential-free; credentials travel only in main-process request bodies or the owning session's cookie jar. A pin change invalidates every affected delegated epoch and blocks new credential-bearing requests until the exact Fleet cookies have been removed from every Desktop jar and affected connections have been retired. Unknown cookie provenance, conflicting hostname pins, or cleanup that cannot be confirmed fail closed. Desktop provenance remains lifecycle compatibility data, never a Console feature mode.
- Every renderer remains sandboxed and Node-free. One local Console view and at most one data Console view may be active in the window's surface lifecycle; a parked view retains no authority over the visible view. Navigation is confined to the /console/ paths of the verified managed Console, verified discovered local Consoles, certificate-admitted remote Consoles, or the active broker-issued epoch. Popups and non-Console navigation remain denied; a data view never forwards a popup to an OS URL handler. Withdrawing an origin removes its active admission, and trust in one host never widens trust in another.
- The entry surface is view-only and one-way. Do not add preload, raw IPC, a renderer fork, a renderer framework, or a Desktop HTTP server.
- Remote access remains headless Desktop plumbing. Console owns host selection UI, saved targets, and trust records; Desktop verifies the selecting surface and never parses access links or maintains its own host store. Pairing credentials remain in Desktop's Chromium cookie storage and are never delegated to Console. For a trusted selection, Desktop performs at most one join and reuses that joined session when choosing a direct or proxied presentation. It may delegate exactly the selected port's remote session cookie, in a main-process body over the authenticated loopback protocol, bound to a registered owner lease, switch generation, pin generation, and idempotent request identity. The broker receives no pairing credential or ability to join. The fleet:// handler only forwards its raw argument to the local Console.
- Host selection comes only from a verified current Console-owned picker on a local main frame, or a native menu or accelerator. A data view may ask to open that picker but cannot select a host, grant a local permission, or spend another host's credential. One native surface state machine owns the active view and the authority for window commands, shortcuts, focus, and Operation Browser views; inactive surfaces cannot command the visible one.
- Display and computer capture require local-ready state and the active local view's main frame on the local /console/, checked both at request start and completion. Before leaving local, the shell obtains a generation-bound acknowledgement from that view that its screen-share and preview tracks, including pending acquisitions, have stopped. Missing or stale acknowledgement cancels the switch; returning to local never silently restarts those tracks.
- A proxied data view uses a unique, never-reused in-memory partition and only a broker-issued epoch origin. Network and native escape paths, permissions, downloads, and navigation are denied outside the approved epoch surface before its first load and throughout teardown. If the required isolation cannot be enforced and verified, proxy presentation is unavailable. Teardown invalidates admission first, stops the view and its workers, and explicitly clears storage, caches, cookies, and connections; destroying a view alone is not cleanup, and forced process termination must not affect another trusted view.
- Desktop uses the Console lock-token trust boundary; token possession does not prove the caller is this Desktop. This does not exempt untrusted renderer code or web content from origin, admission, or permission checks.
- The Operation Browser's native views belong only to the active Desktop surface that holds control of their Console. A joined remote Console may drive Chromium on this machine by product decision, but an inactive surface cannot host hidden browser control. Each browser view remains in its own session partition, never the Console authentication jar. A monitoring-only proxy epoch cannot host Operation Browser control.
- Packaged artifacts remain shell-only; managed Node and Console code is procured into the replaceable Desktop runtime namespace, while state, captures, and locks remain in the Console data namespace.
- Managed Node and Console procurement is staged, checksum-verified, and atomically promoted; installer and sidecar environments preserve their injection- and control-key sanitization. In-session Console update application is only valid when it can preserve this contract and reconnect the owned window; otherwise Desktop relaunches into the entry-flow installer.
- Startup adopts only a protocol-compatible Console owned by the same Desktop; a foreign Console blocks the launch and remains untouched.
- Credential-free local packaging and signed release packaging are separate trust levels. Release paths fail closed, and signing claims require native release evidence.
