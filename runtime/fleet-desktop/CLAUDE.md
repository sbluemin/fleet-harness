# Fleet Console Desktop

`runtime/fleet-desktop` is the optional thin Electron shell for Fleet Console.

## Directory index

| Directory | Responsibility |
|---|---|
| `src/` | Native app, window, menu, tray, and dialog lifecycle |
| `src/runtime/` | Managed Node and Console procurement and supervision |
| `assets/entry/` | Passive bootstrap status surface |
| `assets/browser-chrome/`, `src/chrome/` | Fleet Browser chrome documents and the program main injects into them |
| `scripts/`, `build/` | Packaging and release policy |
| `tests/` | Shell, ownership, packaging, and runtime contracts |

## Constraints

- The Console product remains the sole server, PTY, provider, plugin, durable-state, and React owner. Desktop production source imports only the shared `@fleet-console/protocol` contracts (`desktop`, `lifecycle`, `release`, `remote`) and the leaf foundation packages `@fleet-console/process` and `@fleet-console/lifecycle`; never Console internals. Packaged integration tests remain anchored to the published `@dotobokuri/fleet-console/desktop-protocol` compatibility surface.
- Startup launches the managed Console and hands the single window to its `/console/`. Desktop offers no surface for choosing, adding, or naming a Console — that belongs to the Console product, and a second copy of it here would split the list a user sees. For the Console's sidebar section, Desktop only relays the minimized directory and bounded commands that the Console security constraints define, resolves each command's window-owned opaque id against the home Console, and asks for native confirmation before forgetting a saved Console. A lifecycle command (start, restart) is carried out only for a Console this Desktop manages, judged from the supervisor’s own proof when the command arrives, and only when it comes from a document the home Console serves or, for start alone, after Desktop’s native confirmation; the list’s `local`/`remote` kind, a loopback address, and reachability grant nothing (`../../docs/console-lifecycle-contract.md`, Management, operation, and access path).
- The main process hands the window to `/console/` only after verifying the target's Console identity, and to a remote origin only after confirming its live certificate against the fingerprint the local Console holds for it — confirmed over a plain socket first, because Chromium caches a failed verdict for the whole app run. The browser URL remains token-free: a credential travels in a main-process request body, never in a URL the renderer loads. Desktop provenance stays lifecycle compatibility data, never a Console feature mode.
- Every renderer remains sandboxed and Node-free. Navigation is confined to the `/console/` paths of admitted Console origins — loopback, plus each remote origin whose certificate was confirmed; non-Console navigation and general popups remain denied. Withdrawing a remote origin also clears it from the active origin, and a certificate pin narrows trust to one host without widening it for any other.
- The Fleet Browser is Desktop-owned end to end: its surface (the pane at the main window's right edge, or the detached window), its chrome (address bar and suggestions, tab strip — a vertical rail or a horizontal strip above the address bar — with its context menu, space button and space grid, ⋮ menu, dialogs, annotation editor, toasts, and the guard over the page: the control pill, the agent cursor and the in-control animation), the layout, and the input. Chrome is a set of static, sandboxed, Node-free `file:` documents from `assets/browser-chrome/` (address bar, rail — the tab strip in either orientation —, stage, guard; the divider is a fixed `data:` document) with no preload, raw IPC, or Desktop HTTP server. Main injects one program per document with `executeJavaScript` and pushes state the same way; a document answers only through `console-message` lines from its own exact main frame, which main parses against a fixed action list (`src/chrome/contract.ts`) and rejects on any other shape. Chrome text is rendered with `textContent` only. Colors and dimensions are Console's, mirrored from `theme.css` and gated by the Console design-contract test; chrome follows the Console theme and zoom live. The address-bar view grows over the page for the menu, suggestions, dialogs, and annotation, and the page view stays presented underneath, so the page keeps rendering. Desktop alone places everything: the Console, divider, address bar, rail, stage, and the native page view are set on the same resize, drag, hover, pin, or zoom tick, with no Console round trip. The guard view sits above the page view and below the tab strip: while an agent drives the displayed tab it covers the page so the person's pointer never reaches it and main drops the person's keys to that page, and while the person holds control it covers only the pill. It is a separate document, so nothing it draws enters the page DOM or an agent's screenshot. Console remains the single owner of browser state (tabs, each tab's space membership, the displayed tab, the profile, each space's viewport, and each space's control — agent or person — with the agent's last pointer), agent tools, policy, and the surface lease: the snapshot carries a projection of the tab/space/profile state, and chrome actions return to Console's existing REST routes through the shell's authenticated fetch. The tab strip's shape (pinned, orientation, auto-expand) is Desktop's own preference, kept in its userData state. The other exception is which space the surface shows, which is Desktop's own view state (`src/browser-spaces.ts`): Desktop picks it, remembers each space's last shown tab, follows a displayed tab that moves to another space, and asks Console only to select or deselect a tab. The only thing Console receives from chrome is an image (screenshot or annotation result) handed to its composer. Closing the detached window returns the surface to the pane; renderer replacement, Console/control withdrawal, and main-window shutdown dispose the surface and its views without reviving the main window. This grants no new origin or blanket permission and adds no Console-origin popup: Console can no longer open any browser window.
- This computer's font list goes to the loopback Console's main frame without asking, and to an admitted remote Console only after the user allows that origin in a native dialog. Allow and deny answers live in memory for the app run, so a remote page cannot re-prompt; never grant `unknown` or other permissions wholesale.
- The entry surface is view-only and one-way. Do not add preload, raw IPC, a renderer fork, a renderer framework, or a Desktop HTTP server.
- Remote access lives in Desktop only as headless plumbing: certificate pinning, origin admission, joining, and roster reads. Remote roster reads verify the saved fingerprint; listing must not open sessions, consume one-use grants or move control. Which console to open and what to trust are read from the local Console; Desktop never parses an access link, never stores a host, and writes no credential of its own — the pairing a remote console grants lives in the window session's own cookie jar, and Desktop joins on every open so a paired device resumes without a new link. The registered `fleet://` scheme forwards its raw argument to the local Console and does nothing else with it.
- The Fleet Browser's native views follow the Desktop host to whichever Console it shows, a joined remote Console included: that Console's agent then drives Chromium on this machine, by product decision. Each view lives in its own session partition, never in a Console window's cookie jar, and only the Desktop host that holds control of a Console hosts that Console's views, reparented rather than duplicated between its admitted surfaces.
- Packaged artifacts remain shell-only; managed Node and Console code is procured into the replaceable Desktop runtime namespace, while state, captures, and locks remain in the Console data namespace.
- Managed Node and Console procurement is staged, checksum-verified, and atomically promoted; installer and sidecar environments preserve their injection- and control-key sanitization. In-session Console update application is only valid when it can preserve this contract and reconnect the owned window; otherwise Desktop relaunches into the entry-flow installer.
- Startup adopts only a protocol-compatible Console owned by the same Desktop; a foreign Console blocks the launch and remains untouched.
- Credential-free local packaging and signed release packaging are separate trust levels. Release paths fail closed, and signing claims require native release evidence.
