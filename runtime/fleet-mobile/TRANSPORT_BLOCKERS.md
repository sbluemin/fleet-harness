# Fleet Mobile loopback transport design

Fleet Mobile never gives `WebView` the remote Console origin. The native shell performs the pin preflight, pairing join, and status request, then starts a candidate HTTPS gateway on the target's stable persisted `127/8` alias and port. `WebView` loads only that exact local origin. Each gateway start creates a fresh in-memory P-256 leaf with the exact loopback IP SAN; its private key is never persisted. Each upstream HTTP, SSE, or WebSocket connection is a new TLS socket that verifies the exact remote authority, exact DNS/IP subject alternative name, certificate validity, non-CA leaf status, and SHA-256 DER leaf pin, and negotiates HTTP/1.1 only.

The local gateway requires its exact `Host` and a process-random 256-bit `HttpOnly`, `Secure`, `SameSite=Strict`, path-root cookie. Candidate and active targets use independent host-scoped loopback aliases, ports, certificates, and secrets. Remote cookies stay in Android `CookieManager`, but the shell sends and accepts only the session and pairing cookie names for the selected Console port. Remote `Set-Cookie` values must be host-only and match the Console's exact secure attributes; `Domain`, foreign-port names, malformed attributes, and duplicates fail closed. Accepted values are applied sequentially and are never returned to the local origin. Every enforcing CSP is narrowed to the local HTTPS/WSS authority. This intentionally makes external GitHub and other direct `connect-src` capabilities unavailable in the mobile shell so JavaScript cannot bypass the pinned gateway.

A candidate is committed only after its local `/console/` page completes a nonce-bearing same-origin `/api/v1/status` request through the candidate gateway. Until that point the previous target, gateway, and `WebView` stay active. Candidate failure destroys only candidate state; durable target metadata is written synchronously at commit.

## Proof boundary

Focused JVM/Robolectric tests cover parser, stable-origin selection, local leaf identity, port-scoped host-only remote cookies, cookie rollback, gateway policy logic, and bidirectional relay teardown. The local endpoint itself is HTTPS and the module declares no network-security exception. The promoted APK verifier inspects the final merged manifest and refuses cleartext traffic, alternate network trust, unexpected permissions, or unexpected exported components. Gateway start binds the persisted alias and port exactly and fails loudly if the probe-and-close allocation raced with another binder—there is no silent port or origin mutation. An Android 16 emulator run proves the promoted APK installs, cold-launches its embedded React bundle, loads the native module and WebView process, and stays foreground without a fatal exception. A real access-link integration run is still required to prove vendor `WebView` certificate-callback behavior, long-lived SSE cancellation, and real Console WSS byte relay against a pinned Console. Those are device validation tasks, not reasons for the shell to bypass or weaken the gateway.
