# Isolated Console setup

Build and boot the owned Console before connecting with the selected browser driver. Consult **Isolated Development Data** in `docs/fleet-development-reference.md`. If the run may start Claude (terminal or SDK/chat), complete [Claude state and trust preflight](claude-state.md) first, leaving only its folder-dialog Theater trust step for after boot; Fleet slot isolation alone does not isolate agent state.

## Parallel preparation and commit handoff

When an Objective has an implementer and a separate real-app verifier, use this split for both browser and Desktop work. Set it at lineup planning, not after implementation finishes; retain the existing decisions for current-state measurement, routing, Desktop launch, and PR delivery.

- **Preparation mission:** assign it to the verifier with **no implementation predecessor**. The verifier prepares one owned environment while implementation proceeds.
- **Implementation mission:** require affected builds, typechecks, relevant tests, and a ready commit. Do **not** add the verifier's same real-app acceptance scenarios to the implementer's completion conditions. Keep any necessary implementation-time UI diagnosis narrow, rather than duplicating the acceptance matrix.
- **Verification mission:** its predecessors are **only the preparation mission and the missions producing the implementation commit to check** (the integration mission when applicable), assigned to the same verifier. Board readiness follows declared predecessors only, not a shared assignee, so list preparation explicitly; do not make preparation wait for implementation.

Prepare a verifier-owned [detached comparison checkout](../../git-worktree/references/baseline.md#create) at the selected baseline SHA, install dependencies, and prepare required baseline builds. Keep its source read-only. Do not share or build in the implementer's checkout: concurrent writes can contaminate the observed `dist/` ([record the reproduced build](#record-what-is-being-reproduced)).

Before the implementation commit arrives, prepare the owned [run directory and environment](#isolate-the-console), throwaway Theater, required [Claude state and trust preflight](claude-state.md), seed/fixture and measurement scripts, pre-navigation diagnostics, and a criterion-to-observation table. Keep reusable scripts and notes in the Objective evidence directory. Have those scripts take the run directory, Theater folder, and checkout as arguments or environment overrides instead of fixed paths: the prepared run belongs to the verifier alone, so a Commander's current-state or cross-check measurement boots its own run directory and throwaway Theater and runs the same scripts against them. Baseline-derived selectors, seeds, dependencies, and builds need rechecking against the implementation; preparation is not evidence that the fix passes. For Desktop, complete [preflight and the lineup's launch decision](desktop/setup.md#preflight-and-ownership) during planning, without treating preparation as launch authority.

The implementer's ready handoff identifies the full commit SHA, worktree/branch, affected criteria and packages, and the commands, exit codes, and log paths for its checks. The verifier then:

1. Stops only its owned runtime before changing the checkout. Resolves the reported SHA, visits it as a comparison revision using non-force checkout, and records that visit and the HEAD reflog in evidence. Preserve the baseline's original ownership/creation record and cleanup gates; never edit source or create commits there.
2. Checks source cleanliness and install/build outputs under the baseline contract, reinstalls when dependency inputs changed, and rebuilds affected dependencies and the selected host. Recheck fixtures against the new revision. Keep the same owned run directory; another session cannot inherit it.
3. Binds evidence to the checked SHA, successful build command/exit, local and served asset names, and the owned host's launch/PID from that checkout. Check HEAD and source cleanliness before and after the run. Apply the existing [build, asset, reload, and restart checks](#isolate-the-console); a baseline build or an unchanged running host is not proof of the new commit.
4. Runs the acceptance scenarios with fresh diagnostics and the existing [source-backed observations](verification.md#measure-from-the-source), including applicable screenshots and inverse paths. Report criterion, revision, actual result, raw source and time, cleanup, and unverified scope.

After a fix or rebase, compare the new commit with the checked revision and rerun **only criteria affected by that delta**, including their relevant inverse and regression paths. Retain earlier evidence for unaffected criteria with its original SHA and the reason it still applies; do not relabel it as a new run. Shared dependencies or contracts can widen the affected scope.

The Commander reviews the diff and criterion-to-evidence mapping, directly checking only changed behavior left uncovered or in conflict; do not restart the entire acceptance run ceremonially. Reuse valid evidence through PR workflow's [measured-verification route](../../pr-workflow/references/review-wait.md#measured-verification-route), without weakening its remaining delivery gates.

## Before a paid or long run

During planning, before boot or agent launch, check only the prerequisites the run needs. This additional preflight applies to paid provider calls and runs that may exceed the runner's default background lifetime, not short no-provider screen checks.

- **Runtime contents (paid runs):** during planning, select the check for the artifact this run will execute: [standalone package `dist/index.js`](../../ai-gateway-loop-optimization/references/execution.md#standalone-provider-loop-runner) or [Operation/serve host `dist/cli.mjs`](live-agent-prompt-testing.md#serve-bundle-freshness), which also serves a [headless Claude Code turn](live-agent-prompt-testing.md#headless-claude-code-against-the-owned-console). The executing session must run that check in the target worktree and record its output and return code before the first paid provider call. After **each source edit**, rebuild that artifact and repeat the check before the next first paid call, counting a string this latest edit adds: an earlier edit's marker stays in a stale artifact, so it still passes. When the edit adds no such string (a pure removal), record the rebuild's exit code instead. A previous successful build or check is not evidence for the edited source. A failing check blocks paid calls until the required artifact is rebuilt and passes. Free/no-provider preparation and verification are exempt from this additional content gate, even during a long run; the existing build, isolation, and reload/restart requirements still apply.
- **Runtime lifetime (long runs):** record the expected time from the owned runtime's launch (`serve`, or the Desktop launch) through setup, scenarios, retries, capture, and cleanup, with a margin. Check the chosen runner's current timeout limits and explicitly set the timeout of the managed launch process to cover that whole window; a quick successful boot does not prove that the runtime will survive it. On Desktop, ending the launcher does not stop the app ([Stopping the owned Desktop](desktop/setup.md#stopping-the-owned-desktop)), so a runner timeout leaves the app running unmanaged rather than ending it; the same budget keeps capture and that section's stop helper inside the run. If the window cannot fit, split the run into separately booted, verified segments and keep their evidence separate. Record the selected lifetime with the launch command.
- **Authentication and model exposure (paid runs):** choose a no-provider fixture when it proves the claim; otherwise identify the authorized credential route before boot. Settle from the planned model whether the turn needs the user's own login: only a `claude-gateway--` model runs on the slot's provider sign-ins. Any other Claude model id, including one picked in a gateway Operation, is relayed to Anthropic on the caller's own credential (`relaysUnmatchedModel` and `anthropicNativeHeaders` under `runtime/fleet-console/features/ai-gateway/runtime/src/`), which an owned `HOME` lacks, so a paid turn on it needs the user's Claude login. If the claim needs the user's own login, read [When the claim needs a real login](#when-the-claim-needs-a-real-login) now and prepare its authorization and launch allowlist, rather than discovering the owned-home limitation after a turn. For a client-selected non-Claude gateway model, run the existing [slot model check](live-agent-prompt-testing.md#a-fresh-runtime-directory-exposes-no-gateway-models) against the planned slot now. A fresh slot may need the documented add-model UI after boot: plan that no-cost setup, then repeat the check before launching the Operation or sending a paid call. A failing check blocks paid execution, not the no-cost configuration needed to fix it. Reconfirm the actual launch against real-login step 5 before the first paid call. This preflight checks the launch route and model exposure, not whether the Keychain login is present or valid; leave credential access to the product and keep its existing stop-on-authentication-failure rule.

## Isolate the Console

Never restart or reuse an unknown Console daemon. Build the requested source, choose a unique runtime directory, and start `serve` through [the isolated-environment wrapper](#keep-the-real-home-out) so that no unrelated browser tab opens and no real home is inherited:

```bash
cd <worktree>
export PATH="<pnpm-bin>:$PATH"
pnpm --filter @dotobokuri/fleet-console build
E2E_DIR="<repo-root>/.fleet/e2e-<role>-<short-id>"   # see "Place the run directory" below
node <worktree>/.claude/skills/console-e2e/scripts/isolated-env.mjs --run-dir "$E2E_DIR" \
  -- node <worktree>/runtime/fleet-console/dist/cli.mjs serve
```

The wrapper gives the host and every child it starts `$E2E_DIR/home` as `HOME`, together with `FLEET_DATA_DIR` (`root`), `FLEET_CONSOLE_DATA_DIR` (`console`), `FLEET_DESKTOP_DATA_DIR` (`desktop`), and `CLAUDE_CONFIG_DIR` (`claude`) under the run directory. It passes nothing else from the calling environment, which drops `INIT_CWD`, the parent Console's slot paths, session markers, and tokens. `CLAUDE_CONFIG_DIR` matters even in a UI-only run: adding a Theater through the folder dialog records Claude trust in the host's selected Claude config, which is the user's `~/.claude.json` without it. `FLEET_CONSOLE_DATA_DIR` isolates the Console slot, including credentials, durable state, lock, and gateway selection. The one exception is `--canonical-console-dir <checkout>/.fleet/console` on the wrapper, which points only that variable at the checkout's local slot; [Desktop shell](remote-access-testing.md#desktop-shell) is the run that needs it, and every other owned path stays under the run directory. `FLEET_DATA_DIR` also isolates host-shared data and legacy migration sources, so setting only the Console slot is not a no-user-data-write guarantee. These variables do not isolate Claude: before an agent run, complete the preflight's additional launch checks. (`FLEET_CONSOLE_DIR` is the former name of `FLEET_CONSOLE_DATA_DIR` and still works.)

`dist/cli.mjs` is the `fleet console` entry itself, so its subcommands take no `console` prefix: `cli.mjs console stop` fails with `Unknown fleet console command: console` and leaves the lock. Run `serve` as the managed process and end it with `stop`. `start` and `restart` reuse the Console that the slot's lock names, or spawn a detached `serve` whose output is discarded, so they leave nothing for this run to manage.

**Place the run directory** at `<repo-root>/.fleet/e2e-<role>-<short-id>`, where `<repo-root>` is the main checkout (the first `git worktree list` entry), whose `.fleet/` is git-ignored, and `<role>` is a short tag for this session (an objective member's role, abbreviated) that no other session of the same work uses. It survives a session restart, which objective work needs. When the wrapper refuses it as another session's, choose another name; never stop that Console or delete its directory. Keep the whole path within about 78 bytes on macOS (about 81 on Linux): `tsx` listens on `<run-dir>/tmp/tsx-<uid>/<pid>.pipe`, and a socket path past the OS limit is truncated without an error, so concurrent `tsx` helpers collide. The wrapper refuses a longer run directory with the measured length. The length check decides: a linked worktree's `.fleet/` and the session scratchpad usually exceed the limit. The objective's evidence directory lies under `~/.fleet`, which the wrapper refuses. A throwaway Theater is not a run directory: put it outside every repository, in the session scratchpad, so that neither git nor an agent's parent `CLAUDE.md` lookup reaches the checkout. A Theater that needs git gets its own `git init`. A session restart can remove the scratchpad, so recreate and re-register the Theater after one. Reusing your own run directory is the default, and it is required where state must carry over, such as the verifier's [commit handoff](#parallel-preparation-and-commit-handoff) or a restart claim. A measurement pass whose result assumes an empty slot gets a new name instead (for example a `-2` suffix) and passes `--fresh` on its first wrapper calls (`--check` and `serve`). `--fresh` refuses a run directory that already holds anything, so an earlier pass's Theaters, Operations, or settings cannot mix into the result. It checks only the default `<run-dir>/console` slot, so the wrapper refuses it together with `--canonical-console-dir`.

### Keep the real home out

The Console Shell surface (the toolbar **Shell** button) starts the host's `$SHELL` with the host's `HOME`. A host that inherits the real home therefore writes the user's shell history and reads their startup files. The same holds for measurement commands such as `zsh -i` or a shell startup timing. Earlier runs mixed test commands into the real `~/.zsh_history` this way. Run every owned host, every pnpm or `tsx` helper (such as the onboarding seed below, because pnpm and `tsx` keep caches and state under `HOME`), and every command that starts a shell or an agent CLI through [`scripts/isolated-env.mjs`](../scripts/isolated-env.mjs), with the same `--run-dir`. The exceptions bullet below lists the helpers that run outside it.

```bash
node <worktree>/.claude/skills/console-e2e/scripts/isolated-env.mjs --run-dir "$E2E_DIR" \
  [--fresh] [--bin <name|abs-path>]... [--set NAME=VALUE]... [--check] -- <command> [args...]
```

- **Start checklist, before the first command of a run:** [place the run directory](#isolate-the-console); pass **Before launch** below; route every host, shell, agent CLI, pnpm, and `tsx` command through the wrapper; read the lock only with the [fixed read](#read-the-lock-without-the-token); and stay within **Real-home reads**. The **Self-check** at the end of this list closes the run.
- **Before launch:** run the same invocation with `--check`. It prints the owned directories, the `pathbin` links, `PATH`, `SHELL`, and the names (not values) of `--set` variables, and it starts nothing. The wrapper refuses a run directory, `--bin`, or `--set` path inside the real home's agent, Fleet, shell-history, or credential stores (`~/.claude`, `~/.claude.json`, `~/.fleet`, `~/.codex`, `~/.agent-browser`, `~/.config`, `~/.ssh`, Keychains, shell history and rc files, and similar) or inside an inherited Fleet or Claude directory, after resolving symlinks. It checks each `:`-separated segment of a `--set` value. It resolves every relative segment, including a bare one such as `.claude/x`, against the current directory, where the child also runs. It refuses `~`, because nothing expands it. It also refuses `--set` for the variables it manages and for credential-like names (`*TOKEN*`, `*API_KEY*`, `ANTHROPIC_*`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, `CLAUDE_CODE_CHILD_SESSION`, `SSH_AUTH_SOCK`, ...). It refuses a run directory [owned by another session](#isolate-the-console): one whose `owner` file records a different caller (a hash of the Fleet Operation id or Claude Code session id), even after that session's Console exited, or an ownerless one whose lock, read only for `port` and `pid`, names a live process. This session's own run directory passes after a restart or a forced kill, and the first caller claims an ownerless one exclusively. Fix a refusal by choosing an owned path, never by working around the check. A `--set` path to a probe or preload kept in the objective's evidence directory is refused: copy it into the run directory and pass the copy.
- **`PATH`:** a fresh `$E2E_DIR/pathbin/call-*` directory for each call, then the system directories. It links only the running `node` and that call's `--bin` entries (a name resolved on the caller's `PATH`, or an absolute path), and it is removed when the command exits. A later call on the same run directory therefore never adds a CLI to a host that is already running, such as `--bin claude` reaching a fake-only Console. A Node version manager's directory often also holds globally installed agent CLIs (`codex`, `gemini`, `opencode`, ...), so it is never put on `PATH` whole. Add `--bin pnpm` when the command needs pnpm, and name an agent CLI explicitly, for example `--set CLAUDE_BIN=<worktree>/.claude/skills/console-e2e/scripts/fake-claude.mjs --set FAKE_CLAUDE_DIR="$E2E_DIR/fake-claude"`.
- **Exceptions, stated only here:** outside the wrapper, by design, run the browser driver (agent-browser, Fleet Browser), [`close-owned-session.mjs`](../scripts/close-owned-session.mjs), [`cdp-input.mjs`](../scripts/cdp-input.mjs), and the Desktop helpers ([`desktop-preflight.mjs`](../scripts/desktop-preflight.mjs), [`launch-owned-desktop.mjs`](../scripts/launch-owned-desktop.mjs), [`stop-owned-desktop.mjs`](../scripts/stop-owned-desktop.mjs), [`main-inspector.mjs`](../scripts/main-inspector.mjs), [`resize-owned-window.mjs`](../scripts/resize-owned-window.mjs)). These locate sessions under the real home or only talk to an owned endpoint. So do plain-Node HTTP helpers that start no shell, agent CLI, pnpm, or `tsx`, such as [`fake-claude-mcp.mjs`](../scripts/fake-claude-mcp.mjs) and console-handoff's `seed-console.mjs`, and the workspace install and build (`pnpm install`, `pnpm --filter … build`), which write only the checkout and pnpm's own store and start nothing under the run. Workspace tests (`vitest`, `pnpm test`) that use their own fixtures and act on no E2E run also run outside it. Inside the wrapper `os.tmpdir()` is `<run-dir>/tmp`, under the main checkout, so a fixture that must not be a Git repository finds the parent repository, and three non-Git cases in `file-explorer` and `repository` failed falsely (measured 2026-10-23). `--set GIT_CEILING_DIRECTORIES` does not fix it, because the product's git calls drop inherited `GIT_*` variables. A test or measurement helper that operates on the owned run still runs inside. Inside it run the host's own launcher commands, including `cli.mjs stop` with the same `--run-dir`, so that it never sees an inherited Fleet root. A Desktop launch keeps its own owned-`HOME` allowlist in [Desktop setup](desktop/setup.md), because macOS `open` relaunches the bundle with the caller's environment. On Windows, where the wrapper does not run, apply the same owned-path allowlist by hand and report it as such. The one credential-like value the wrapper forwards is the fixed local placeholder `--set ANTHROPIC_API_KEY=sk-ant-fleet-local`, which is not a credential (see [the headless launcher](live-agent-prompt-testing.md)). Any other real store — the user's Claude home, an environment credential, the real Fleet root — needs the user's explicit authorization for that store. Such a run starts outside the wrapper, is disclosed before launch per the [Claude state preflight](claude-state.md), and is reported as non-isolated for that store. [When the claim needs a real login](#when-the-claim-needs-a-real-login) is that route for the user's own Claude or Cursor login.
- **After the run:** the wrapper reports which entries appeared in the owned home. After a shell ran in the Shell surface, `.zsh_history` (or the shell's equivalent) there is the positive evidence that history went to the owned home. For a stronger check, type a unique no-op marker such as `: fleet-e2e-<unique-id>` in that shell, close it, and confirm that `grep -c` finds it in `$E2E_DIR/home/.zsh_history`.
- **Real-home reads:** the only reads of real-home files allowed are the scoped digests in the [Claude state baseline](claude-state.md#record-the-baseline-before-any-child-starts) and `grep -c <unique marker>` against the user's shell history file, which prints a count only and should find 0. A denied read leaves that check unverified, not clean. Never print or copy real-home file contents. The whole of `~/.claude` is real home, including auto-memory under `~/.claude/projects/<project>/memory/`, other sessions' transcripts and `projects/` records, settings, and plugin data. Apart from the baseline's scoped checks there (named-file digests and this Theater's trust entry or `projects` directory), listing, searching, or opening anything under `~/.claude` is a read outside this allowance. Memory that the agent harness itself loads into context at session start is not a read by the run.
- **Process listings:** identify processes only by the PIDs and ports recorded for this run, and print only the columns the check needs, for example `ps -p <pid> -o pid,ppid,stat,etime` or `lsof -nP -iTCP:<owned port> -sTCP:LISTEN`. Print a command line only where a lane needs it to prove what an owned PID runs, and then only for that PID. An agent CLI's command line carries the Console-issued MCP bearer tokens in its inline `--mcp-config`, so never print or log an agent child's command line, even an owned one: use `ps -p <pid> -o comm=` or a `grep -c` count, and make a process tracer or preload record only the executable basename and subcommand. A whole-table `ps` or `pgrep` listing such as `ps aux`, `ps -ef`, `pgrep -fl`, or `pgrep -af` prints other sessions' command lines, which can carry paths, prompts, and tokens. An `lsof` that is limited neither to a recorded PID (`-p`) nor to an owned port (`-iTCP:<port>`) lists other sessions' processes and files. The Desktop helpers read the process table internally and print no command line or environment. Besides owned PIDs and the listeners on the ports they check, `desktop-preflight.mjs` prints the PIDs and executable paths of the caller's ancestor chain and responsible process. In `--occlusion` mode it also prints the app names and PIDs of other windows that cover the owned window. A process's environment is never printed (see [Claude state](claude-state.md)).
- **Self-check before reporting:** confirm that each command that started a host, a shell, an agent CLI, or a pnpm or `tsx` helper for the run went through the wrapper. Confirm that no real-home read went beyond the allowance above, including anything under `~/.claude`. Confirm that no process listing went beyond the run's own PIDs, that no output, including an error message, printed a lock body, token, or ticket, that recorded WebSocket and network URLs dropped their query string, and that no command ran `security`, `login`, or token-refresh helpers. Report a command that ran outside the wrapper as a possible leak with its effect, rather than declaring the home untouched. Report a read or a listing beyond these bounds the same way: name the command and what it exposed.

The wrapper is an environment boundary for macOS and Linux, not an OS sandbox. It does not isolate the macOS Keychain (see [credential limits](claude-state.md#select-a-child-route-not-just-an-environment-variable)), launchd session keys that `open` adds to a Desktop launch, or network access, and a child can still write to an absolute path it is given. The self-check above applies to the exceptions as well.

A fresh slot has no provider credentials. Do not copy real credentials, trigger login/token refresh, or silently reuse a user's root to make a test pass. Prefer a no-provider fixture when it proves the claim. A real-provider scenario needs an explicitly authorized credential path and quota use, with any non-isolated stores disclosed before launch.

Run the server as a background/managed process with the lifetime selected in [long-run preflight](#before-a-paid-or-long-run) when applicable, wait for `$E2E_DIR/console/console.lock`, read its port with the fixed read below, and confirm the route returns `200`. Seed a real Theater through the Console folder UI or authorized API only when the scenario needs it; do not copy the user's durable state. An API-registered Theater stays untrusted for Claude, so a terminal Operation that must receive a Console prompt needs the folder-UI route in [the trust preflight](claude-state.md#prepare-folder-trust-through-the-normal-gate).

Client changes require build plus reload. Host changes require build plus isolated server restart. Compare the asset name in `dist/client/index.html` with the served `/console/` HTML before blaming stale behavior.

#### Read the lock without the token

Print only `port` and `pid` with this fixed read. It catches a parse failure itself, because a JSON error message quotes part of the file:

```bash
node -e 'try { const l = JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")); if (!l.port || !l.pid) throw 0; console.log(JSON.stringify({ port: l.port, pid: l.pid })); } catch { console.error("console.lock not readable yet"); process.exit(1); }' "$E2E_DIR/console/console.lock"
```

Never `cat`, `jq`, or `grep` the lock, and never put the token in a shell variable, a URL, or a command line. A step that needs the token reads it inside the one Node process that sends the request and passes it only as a header, as [`issue-access-link.mjs`](../scripts/issue-access-link.mjs) does.

#### Restart after a forced kill

A Console that exits without its shutdown handler (`SIGKILL`, a capped kill, a crash) leaves `$E2E_DIR/console/console.lock` holding its dead PID. The next `serve` on that run directory then exits 1 within a second with `EEXIST: file already exists, open '<run-dir>/console/console.lock'`. Handle only the lock of this run's own `$E2E_DIR`, and never delete it by hand:

1. Take `pid` from the [fixed read](#read-the-lock-without-the-token).
2. Probe it with `node -e 'try { process.kill(Number(process.argv[1]), 0); console.log("alive"); } catch (e) { console.log(e.code); }' <pid>`, and continue only on `ESRCH`. For any other result, do not run `stop`: it signals whatever process now holds that PID, so a reused PID would receive `SIGTERM` and then `SIGKILL`. Prove the PID is this run's `cli.mjs serve` from the recorded worktree by comparing its command line without printing it, for example `ps -p <pid> -o command= | grep -cF '<worktree>/runtime/fleet-console/dist/cli.mjs serve'`, since a reused PID is not owned and the [process-listing bounds](#keep-the-real-home-out) allow printing only an owned PID's command line. If it is, a live owned Console holds the lock, so stop and restart it normally. If it is not, stop and report it.
3. Run `cli.mjs stop` through the [wrapper](#keep-the-real-home-out) with the same `--run-dir`. With a dead PID, `stop` only removes the lock.
4. Start `serve` again as in [Isolate the Console](#isolate-the-console), with the same wrapper flags as the first boot (such as `--set CLAUDE_BIN=…`), then take the new port with the fixed read.

#### When the claim needs a real login

Use this route only when the claim needs a model turn that only the user's own login can authenticate, and no fixture or authorized slot credential proves it. The Claude CLI reads that login from the macOS Keychain or a credential file under the real home, so an owned `HOME` cannot see it. AI Gateway Codex, xAI, Cursor, and Muse Code sign-ins live only in the Console slot's `auth.json`, so this route cannot supply them. Step 2 replaces only the wrapper's launch of `serve` and its `--check`; every other rule in [Keep the real home out](#keep-the-real-home-out) still applies.

1. **Authorize before launch.** Get the user's authorization for this run's use of the real Claude home and Keychain logins, its paid calls, and the cleanup in step 6. Disclose before launch that the run is not isolated from those stores, per the [Claude state preflight](claude-state.md), and record its [baseline](claude-state.md#record-the-baseline-before-any-child-starts). Register a [throwaway Theater](#isolate-the-console) so that the records the run leaves are identifiable.
2. **Launch outside the wrapper with a hand-built allowlist.** First claim the run directory through the wrapper with a no-op, `isolated-env.mjs --run-dir "$E2E_DIR" -- true`, so that its [ownership check](#isolate-the-console) refuses another session's directory and records this one as owned; stop on a refusal. Then start `serve` under `env -i` with only the real `HOME`, `USER` and `LOGNAME` (a Keychain lookup fails without them), a `PATH` built as the **`PATH`** bullet above describes, `CLAUDE_BIN`, and the three Fleet paths in owned slots: `FLEET_DATA_DIR=$E2E_DIR/root`, `FLEET_CONSOLE_DATA_DIR=$E2E_DIR/console`, `FLEET_DESKTOP_DATA_DIR=$E2E_DIR/desktop`. The Fleet paths are mandatory: the real Fleet root holds the user's Console slot and the legacy sources a fresh slot migrates. Leave `CLAUDE_CONFIG_DIR` unset, because relocating it changes the Keychain service identity ([credential limits](claude-state.md#select-a-child-route-not-just-an-environment-variable)). Never add `CLAUDE_SECURESTORAGE_CONFIG_DIR`, a token, or the caller's session variables. Run `cli.mjs stop` with the same environment, and do not open the Shell surface, which would write the real shell history.
3. **Leave the Keychain to the product.** Only the Console and the agent CLI read it. Never run `security`, a login or logout, `/login`, or a token-refresh helper, and never open a credential file. When a launch reports `Not logged in` or the provider rejects the login, stop and report an environment block instead of logging in.
4. **Keep tokens out of every output.** The lock-read, process-listing, and environment rules above apply unchanged. Record an authentication or provider failure as its status code and a classification, never its raw message or response body.
5. **Spend as few paid calls as the claim needs.** Before the first one, confirm without spending that it can succeed. The Console it goes to must be the step 2 launch: a `serve` started through the wrapper has an owned `HOME` and cannot see the login, so its turn stops at `Not logged in`. Judge that from the launch command you ran, never by querying the Keychain or printing a process environment. If it fails, stop with no paid call and report an environment block. Use short prompts, and report how many turns ran on each model.
