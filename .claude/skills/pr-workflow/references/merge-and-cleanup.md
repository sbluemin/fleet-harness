# Final audit, merge, and cleanup

### Phase 6 — Auto-merge

Reached after Phase 3 confirms review completion (a fresh Codex `+1` with no open actionable comments), the Phase 3 stop rule (a pass with no FIX-class finding, or the third pass), `REVIEW_BYPASS_REASON=codex_activation_timeout` from the bounded explicit activation gate, or `REVIEW_BYPASS_REASON=codex_usage_limit` as the Phase 3 usage-limit classification sets it ([Review wait](review-wait.md#classify-what-codex-actually-reviewed)). None of these signals proves product correctness, and the final context audit below gates the merge in every case. The timeout and usage-limit fallbacks authorize normal merge checks only; it never bypasses branch protection or required checks. When `<auto_merge>` is `false`, skip merging and report the PR as review-complete-but-unmerged or review-unavailable-and-unmerged.

**Review-fix re-check gate.** The gate's scope is every PR change in the head about to merge that the last Codex-reviewed head lacks: review FIX commits, mission- or user-directed commits added after that review, and content a rebase changed. The last Codex-reviewed head is the latest SHA in the *Run completed* or *Current head reviewed* state in [Review wait](review-wait.md#classify-what-codex-actually-reviewed), or the `commit_id` of a Codex review object (the review itself, not its inline comments, whose `commit_id` re-anchors); with none, the scope is the remaining FIX commits. A non-empty scope needs one of these before merge:
- (a) Codex reviewed the current head: the *Current head reviewed* state.
- (b) An independent re-check: an objective member that did not write or apply the changes in scope, or a separate reviewer session, checks each FIX item and each other commit in scope, with its hunks, and records the SHA it checked with a result per item as a PR comment. A reviewer without permission to post sends that record to this workflow's session, by message or as sealed objective evidence, and this session posts it verbatim, naming the reviewer and the source, with no verdict of its own. A re-check covers only the SHA it records; it passes the gate for the head about to merge when that SHA is the head, or when the range-diff rule below carries its coverage to the head.
- (c) A merge directive from the person that still stands after you have told them the actual review state and listed the changes in scope that nothing re-checked. Only the person counts, through their own direct message or their own board answer: a Commander, member, Commodore, or other agent session relaying, issuing, or answering a decision with a merge instruction is not a user directive, nor is silence after the disclosure. A member raises the disclosure with its Commander, who asks the person. The lifecycle authorization or a mission's merge instruction given before that disclosure does not count, and asking is not an ordinary step. Then post `REVIEW_BYPASS_REASON=user_directed` with that list as a PR comment before merging.

The local verification of the unreviewed delta that `codex_usage_limit` requires is necessary but never satisfies this gate, and neither does any wait timeout. A re-check is not a review pass and does not count toward the three-pass default. After the third pass, do not wait for another Codex run to clear the gate: a Codex review already on the current head counts as (a); otherwise use (b) or (c). A defect the re-check reproduces goes back to Phase 4. Whenever a covering SHA — the last Codex-reviewed head or a re-checked SHA — differs from the head about to merge (added commits, or a rebase including a step 4 integration rebase), judge by content with `git range-diff <old-base>..<covering-sha> <new-base>..<head>`, each base being that SHA's merge base with a freshly fetched `origin/<base>`: a patch shown as `=`, or as `!` whose outer `-`/`+` lines are all inner context lines (inner marker a space) or `@@` headers, keeps that SHA's coverage. Every other entry enters the scope: any other `!` patch, a new one (`-: ------- > n:`), or a dropped one (`n: … < -: -------`), and so does any merge commit after the covering SHA, which range-diff skips. Without (a), (b), or (c), halt the merge: Phase 7 then keeps the branch and worktree and reports the PR as `review-fixes-unverified-and-unmerged`.

**Canary-only CI pre-check.** PR checks do not run the workspace typecheck or test; jobs that start only on a `<base>` push run them after the merge, when a failure has already turned `<base>` red. Find those jobs each time rather than from a remembered list: in `.github/workflows/`, a workflow whose `on.push.branches` includes `<base>` and that has no `pull_request` trigger, or a job whose `if:` skips pull requests. Compare each one's `paths`/`paths-ignore` with `git diff --name-only origin/<base>...HEAD`. For every job that will run, execute its commands in the head worktree under **Isolated Development Data** in `docs/fleet-development-reference.md`, narrowed to the changed workspace packages plus every package or repository-wide check that consumes or scans the changed files, including cross-package source-scanning gates (a built-in plugin change also runs the Console-owned tests that scan or bundle it). Find those by searching other packages' tests and `scripts/` for the changed paths (for example `grep -rl 'fleet-plugins/' runtime/*/tests scripts`); a package dependency filter misses them. Run at minimum `pnpm --filter <pkg> typecheck` and `test` for each such package, plus any job-specific command touching them, and run the job's full command when a shared contract, dependency, or the lockfile changed or the scope cannot be settled. Record each job as passed locally or not runnable here (for example a Windows-only job on a POSIX host); the latter relies on step 7. The evidence must cover the head about to merge. Diagnose a local failure: one this change causes is fixed as a head commit, which enters the re-check gate scope; an unrelated or environmental blocker is reported without widening the scope.

1. **Stop the wait loop.** If Phase 3 started a background poll, stop it with `TaskStop` (or `CronDelete` for the cron fallback). Under `codex_activation_timeout`, no long-running poll exists; continue directly. No more review polling occurs after this point.
2. **Run the final context audit against a recorded base.** Fetch `origin/<base>`, record its SHA as `FINAL_AUDIT_BASE`, and record the current PR file set with `gh pr diff <pr_number> --repo <repo> --name-only`. Compare the cumulative review-driven diff from `REVIEW_BASE_HEAD` to the frozen Product Context Record. Confirm every hunk remains in original scope, preserves supported behavior and intended trade-offs, and has proportional user/operator value. On drift, roll back the drift and return to Phase 5 for validation/re-review; if rollback or product intent is ambiguous, stop and ask the user. Never merge merely because Codex approved.
3. **Check base freshness and mergeability.** Fetch `origin/<base>` again immediately before interpreting `gh pr view <pr_number> --repo <repo> --json mergeable,mergeStateStatus,baseRefName,headRefName`.
   - If `origin/<base>` advanced past `FINAL_AUDIT_BASE`, inspect the returned file list and relevant diff in `FINAL_AUDIT_BASE..origin/<base>` against the recorded PR file set. Any overlap → go to step 4 even when GitHub reports `MERGEABLE / CLEAN`; textual mergeability does not prove the combined same-file behavior. With no overlap, also judge whether changed dependencies or shared contracts invalidate the audit or validation evidence. If compatibility cannot be established, halt the merge and report the concrete integration/validation blocker rather than merely moving the recorded base forward. Only after recording why the advance is compatible may you update `FINAL_AUDIT_BASE` and continue.
   - `mergeable: MERGEABLE` with `mergeStateStatus` `CLEAN` / `UNSTABLE` / `BEHIND` and neither overlapping base advance nor unresolved dependency impact → go to step 5 (merge directly).
   - `mergeable: CONFLICTING` or `mergeStateStatus: DIRTY` → go to step 4.
   - `mergeable: UNKNOWN` → GitHub is still computing mergeability; wait briefly and re-check before deciding.
4. **Integration path — rebase the head onto `<base>`, then force-push.**
   1. Invoke the **rebase-on-canary** skill against the PR head (current-branch mode in the head's worktree, or its explicit `<worktree_path>`) with base = `<base>`. By default that skill auto-resolves conflicts by integrating both sides and validates the result.
   2. rebase-on-canary escalates only a genuinely ambiguous/unsafe conflict or a post-rebase validation failure. If it escalates, **halt auto-merge** and surface its report to the user — do not merge.
   3. On a successful rebase (clean or auto-resolved), run the available tests, typecheck, and build for every workspace affected by the overlapping files; a textually clean rebase does not waive integration validation. Confirm the current branch is `<headRefName>`, then publish the rewritten history with a lease: `git push --force-with-lease origin HEAD:<headRefName>`. Never `--force`; never force-push `<base>`.
   4. Wait for the rewritten head's remote checks, repeat the final context audit (step 2), then re-check base freshness and mergeability (step 3). If validation, CI, mergeability, or context fails, halt and escalate; never merge an integration result that changed product intent or supported behavior.
5. **Separate the final decision from merge execution.** Fetch `origin/<base>` once more and repeat step 3 in a read-only tool call. Wait for its output, inspect base advancement, file overlap/dependency impact, and mergeability, then record the go/no-go decision with the audited base, PR head SHA, and canary-only CI pre-check outcome. Do not put this inspection and `gh pr merge` in the same Bash call, shell chain, script, or parallel tool batch: a successful inspection command is not the judgment of its output. If the decision is go, immediately run `gh pr merge <pr_number> --repo <repo> --<merge_method>` in a separate subsequent tool call (default `--squash`, matching the repo convention). If intervening work or new head/base information makes the decision stale, repeat the inspection and judgment first. Do not pass `--admin` or otherwise bypass branch protection or a required check — if the merge is rejected, halt and escalate.
6. **Verify the merge.** `gh pr view <pr_number> --repo <repo> --json state,mergedAt,mergeCommit` — confirm `state: MERGED` and record the merge commit SHA.
7. **Watch the merge commit's `<base>` CI.** Take the full `mergeCommit.oid` from step 6 and derive the candidate workflows: those triggered by a `<base>` push whose `paths`/`paths-ignore` match the PR's file set from `gh pr diff <pr_number> --repo <repo> --name-only`, which needs no fetch (a docs-only change legitimately starts none of the path-filtered ones). List the runs with `gh run list --repo <repo> --branch <base> --commit <full-sha> --event push --json databaseId,workflowName,status,conclusion`. A short SHA and a not-yet-registered SHA both return `[]` with exit 0, so an empty or partial list is never a pass: re-query about every 10 seconds until every candidate workflow has a run. The PR file set can name files the base already had, so a candidate still missing after 5 minutes is a blocker only when the actual push also triggers it: `git fetch origin <base>` and match its filters against `git diff --name-only <before> <sha>`, `<before>` being the `<base>` head the merge landed on (`<sha>^` for a squash or merge commit, `<sha>~<n>` for an n-commit rebase). Wait on each run in the background with `gh run watch <id> --repo <repo> --exit-status`, which exits non-zero on failure. On a red run, read `gh run view <id> --repo <repo> --log-failed`. When the failure comes from this change, report the cause and run id. Only when this delivery's authorization covers restoring `<base>` (for example, the request asked for a green `<base>` after merge), start a separate repair-PR lifecycle of this skill on a fresh `git-worktree` branch with every gate intact (this PR's flow is finished, so this is not a mid-flow branch), and repeat this step on its merge commit; otherwise ask for that authorization. A failure this change did not cause is reported, not repaired. Record each run id with its workflow and conclusion.
8. Go to Phase 7.

### Phase 7 — Cleanup & completion

**Autonomous cleanup (only when the merge succeeded).** When Phase 6 confirmed `state: MERGED`, clean up the merged head branch's local artifacts yourself — do **not** ask the user. Follow the git-worktree skill's remove flow:
1. If `<headRefName>` is in this task's dedicated worktree, invoke `git-worktree` remove mode. That skill owns protected/dirty/unpushed/ownership checks and removal commands.
2. If the user authorized direct work in the main checkout, first confirm its current branch is `<headRefName>`, clean, and unprotected. Then switch to `<base>` and delete only the merged head branch. Otherwise preserve user changes and report incomplete cleanup.
3. Hard stops — never cross even autonomously: never delete the main checkout, and never delete a protected branch (`main` / `master` / `<base>`). The remote head branch is typically auto-deleted by GitHub on merge; otherwise leave it unless remote cleanup was requested.
4. Skip cleanup entirely when `<auto_merge>` is `false` or the merge halted — the branch and its worktree must survive for follow-up.

Then report in Korean:
- PR number, title, head/base, URL, draft flag.
- Frozen Product Context Record evidence, `REVIEW_BASE_HEAD`, `FINAL_AUDIT_BASE`, and the final cumulative context-audit outcome.
- Each review item across all passes: fix / declined / deferred, with verification evidence.
- Files changed, the initial commit SHA (fragment included when a feature-level note was warranted), later fix commit SHA(s), and push target(s).
- Validation commands and pass/fail status; note any check not run. Include the canary-only CI pre-check per job (passed locally, or not runnable here) and the step 7 `<base>` run ids with their conclusions, plus any follow-up repair PR.
- The approval signal observed (Codex `+1` on the PR body), the explicit activation request URL plus `codex_activation_timeout`, or the usage-limit comment URL plus `codex_usage_limit` with the last reviewed commit (or none) and the locally verified unreviewed delta; include every `@codex` follow-up comment URL. When the re-check gate applied, add the basis that passed it and its evidence.
- **Merge outcome**: merged (`<merge_method>` + merge commit SHA + whether a pre-merge rebase/force-push was needed), or — when `<auto_merge>` is `false` or auto-merge halted — the approved-but-unmerged state and the reason, or `review-fixes-unverified-and-unmerged` with the changes in scope that nothing re-checked when the re-check gate halted it. The Phase 3 wait poll was stopped in Phase 6.
- **Cleanup outcome**: worktree removed / local branch force-deleted, or skipped (with reason).

**Objectives mission.** When this run is a mission of a Fleet Objectives objective (the session holds an objective role), the report does not end the turn, whether the PR merged, halted, or stayed unmerged. In the same turn, right after the outcome is settled (and cleanup when merged), the Commander completes the mission or records why it is blocked, then takes up the next ready mission or states that none remains; a member reports the result or the blocker to its Commander and stops there. This holds when a direct user message such as "merge and clean up" started the turn. Outside an objective, nothing here changes.

## Documentation Synthesis

PR titles, summaries, bodies, and `.changelog.d/` fragments are host-owned. Synthesize them directly from the frozen Product Context Record, verified `git diff`/`git log` evidence, and validated changelog fragments — never delegate documentation synthesis.

## Safety Rules

- Do not push commits directly to `main` / `master` / `<base>` or any protected branch — local pushes target only the PR's `headRefName`. Phase 6 integrates into `<base>` exclusively through the server-side `gh pr merge`, never a local push to the base.
- Do not address review items outside `<scope_hint>` that the user did not ask for.
- Do not treat reviewer severity, re-review comments, or approval as scope or product-policy authority; the frozen Product Context Record governs every pass and the final merge audit.
- Do not silently expand scope: no opportunistic refactors, formatting-only churn, or dependency bumps.
- Do not create a new branch mid-flow, amend, or close/reopen the PR. Do not rebase or force-push **except** the Phase 6 integration path: it rebases the head onto `<base>` for a textual conflict or overlapping post-audit base advance via the rebase-on-canary skill and force-pushes the result to `<headRefName>` with `--force-with-lease` only — never `--force`, never to `<base>`.
- Phase 6 merges only via `gh pr merge` with `<merge_method>` (default `squash`); never pass `--admin` or bypass branch protection or a required check — halt and escalate if the merge is rejected.
- Do not bypass Git hooks (`--no-verify`, `--no-gpg-sign`, etc.) without explicit user permission.
- Do not commit secrets, `.env` files, or generated artifacts that are not part of the change.
- Do not write commit messages in any language other than English.
- Do not post the `@codex` follow-up until the push has succeeded and the commit is visible on the remote.
- Do not invent validation results — if a check was not run, say so.
- Phase 7 autonomous cleanup runs only after Phase 6 confirms `state: MERGED`; it force-deletes only the merged head branch and its worktree, never the main checkout or a protected branch (`main` / `master` / `<base>`).
- Create PRs only against `sbluemin/fleet-harness` with this skill.
