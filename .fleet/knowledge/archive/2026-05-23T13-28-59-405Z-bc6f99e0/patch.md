Overview\n\nFleet의 내부 MCP 도구 표면을 단일 서버에서 두 개의 독립 서버로 분리하는 결정입니다. 이전에는 모든 내부 도구가 하나의 서버 이름 아래에 노출되었으나, 이제는 캐리어 오케스트레이션 도구와 위키 지식 도구가 각자의 서버를 통해 독립적으로 제공됩니다.\n\n이 결정은 Fleet의 내부 도구 표면이 두 개의 명확히 다른 도메인 — 캐리어 운영과 지식 관리 — 로 성장하면서, 단일 서버가 두 도메인의 경계를 흐리게 만드는 cognitive debt를 해소하기 위한 것입니다.\n\n## Problem\n\n- **의미적 과부하**: 단일 서버 이름이 캐리어 발송, 작업 모니터링, 위키 검색, 패치 승인과 같이 성격이 전혀 다른 도구를 모두 포괄하여, 운영자가 \"이 서버에는 어떤 도구가 있는가\"를 직관적으로 판단할 수 없었습니다.\n- **학습 비용 증가**: 신규 기여자가 Fleet의 도구 표면을 처음 접할 때, 어떤 도구가 어떤 도메인에 속하는지 파악하기 위해 전체 카탈로그를 탐색해야 하는 반복적인 cognitive cost가 발생했습니다.\n- **충돌 위험**: 모든 도구가 하나의 네임스페이스를 공유하여, 도메인이 다른 두 도구가 개념적으로 충돌하거나 혼동될 가능성이 커졌습니다.\n- **스코핑 복잡성**: 서로 다른 보안 경계를 가진 도구들이 동일한 연결 지점을 공유하여, \"어떤 도구를 누가 볼 수 있는가\"를 결정하는 로직이 점점 복잡해졌습니다.\n\n구조적 원인은 Fleet의 도구 표면이 처음에는 소규모였기 때문에 단일 서버가 합리적이었지만, 시간이 지나며 캐리어 도메인과 위키 도메인이 각각 독립적인 생태계로 성장했기 때문입니다. 캐리어 도구는 LLM 실행을 오케스트레이션하는 운영 표면이고, 위키 도구는 지식을 생성하고 관리하는 지식 표면입니다. 이 두 표면은 사용자도 다르고, 보안 경계도 다르고, 생명주기도 다릅니다. 그럼에도 불구하고 하나의 전송 표면을 강제로 공유하게 되자, 도메인 경계를 서버 수준이 아닌 점점 복잡한 레지스트리 필터링으로 흉낼 수밖에 없었습니다. 이것이 \"왜 이 도구들이 함께 있지?\"라는 질문을 끊임없이 낳는 cognitive debt의 뿌리였습니다.\n\n## Goals\n\n- 도메인에 맞춘 서버 표면을 확립하여, 서버 이름만 보고도 어떤 도구가 노출되는지 직관적으로 알 수 있게 합니다.\n- 서버 경계에서 도구 격리를 실현하여, 스코핑이 연결 수준에서 자연스럽게 이루어지게 합니다.\n- 독립적인 생명주기를 부여하여, 각 서버를 별도로 가동, 중지, 토큰 관리할 수 있게 합니다.\n- 학습 곡선을 낮추어, 신규 기여자와 운영자가 도구 위치를 즉시 판단할 수 있게 합니다.\n\n## Non-Goals\n\n- MCP 전송 프로토콜 자체나 레지스트리 내부 메커니즘의 변경.\n- 새로운 도구 추가나 기존 도구 제거.\n- 도구 호출 계약이나 파라미터 스키마의 변경.\n- 외부 MCP 서버와의 통합이나 병합.\n\n## User Stories\n\n- **As a** 캐리어 운영자, **when** 전용 CLI 세션을 구성할 때, **then** 두 개의 독립된 MCP 서버 항목과 각각의 토큰을 받아, 어떤 도구가 어떤 목적을 위해 존재하는지 명확히 알 수 있습니다.\n- **As a** Fleet 관리자, **when** 특정 캐리어가 접근할 수 있는 도구를 검토할 때, **then** 필터링된 도구 목록을 파싱하지 않고 서버 연결 자체로 접근 범위를 추론할 수 있습니다.\n- **As a** 신규 기여자, **when** Fleet의 도구 표면을 처음 탐색할 때, **then** 캐리어 오케스트레이션 도구와 위키 지식 도구가 서로 다른 서버에 살고 있다는 사실을 즉시 이해할 수 있습니다.\n- **As a** 도구 개발자, **when** 새로운 위키 지식 도구를 추가할 때, **then** 캐리어 오케스트레이션 도구의 네임스페이스를 고려할 필요 없이 위키 서버의 범위 안에서만 작업할 수 있습니다.\n\n## Functional Requirements\n\n- Fleet은 두 개의 독립적인 내부 MCP 서버를 노출하며, 각 서버는 고유한 정체성을 가집니다.\n- 캐리어 오케스트레이션 도구는 캐리어 서버를 통해서만 접근 가능합니다.\n- 위키 지식 도구는 위키 서버를 통해서만 접근 가능합니다.\n- 각 서버는 세션별로 독립적인 Bearer 토큰을 발급하며, 토큰은 서버 경계를 넘어 유효하지 않습니다.\n- 전용 CLI 주입은 두 서버를 별도의 MCP 설정 항목으로 전달합니다.\n- 실행기 세션의 도구 스코핑은 서버별로 해결되며, 병합된 카탈로그를 대상으로 하지 않습니다.\n\n## Acceptance Criteria\n\n- [ ] 전용 CLI 세션이 두 개의 별도 MCP 서버 설정을 각각 다른 이름과 토큰으로 수신하는가?\n- [
