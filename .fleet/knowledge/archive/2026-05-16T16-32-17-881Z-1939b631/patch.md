{"id":"prd-coding-agent-empty-session-guard","title":"PRD: Coding Agent Empty Session Guard","tags":["coding-agent","session-selector","persistence","durable-commit","shipped"],"created":"2026-05-16T16:32:17.881Z","updated":"2026-05-16T16:32:17.881Z","version":1,"body":"# Overview\n\nThis document defines the structural decision to prevent the accumulation of redundant temporary sessions labeled `(no messages)` within the coding-agent TUI session selector. By redefining the persistence lifecycle to favor in-memory state with deferred durable commits, the system ensures that only sessions containing meaningful user-assistant interaction reach long-term storage.\n\n# Problem\n\nThe previous state suffered from significant cognitive debt and UI friction caused by \"ghost sessions.\" Every time a user opened a new session, initialized an agent, or issued a custom command, the system would immediately flush host/carrier mapping entries or trigger synchronous disk writes to the session's JSONL file. \n\nThe structural cause was the lack of a unified \"significance threshold\" for persistence. Write operations were scattered across multiple sender-origin paths—including connection events, store updates, and shutdown hooks—rather than being gated by the first successful round-trip of message exchange. This resulted in a cluttered TUI selector where meaningful work was buried under dozens of empty, system-generated session files.\n\n# Goals\n\n- Eliminate the creation of `(no messages)` session files on disk during initialization or idle sessions.\n- Unify session identification by phasing out synthetic IDs in favor of a single, authoritative identifier shared across the host and the Grand Fleet.\n- Transition the session runtime to an \"in-memory-primary\" model where durable commits are deferred until a transaction is validated as meaningful.\n- Resolve the clutter problem through a \"principled front-end\" approach (root cause resolution) rather than reactive measures.\n\n# Non-Goals\n\n- Implementing a background \"sweeper\" service to delete existing empty files.\n- Hiding empty sessions from the UI selector while leaving them on disk.\n- Adding complex retry loops or heuristic-based session recovery for failed initializations.\n- Modifying the persistence behavior of ephemeral session domains that are intentionally detached from long-term history.\n\n# User Stories\n\nAs a developer using Fleet, I want the session selector to reflect only the work I have actually started, so that I can quickly navigate between relevant task histories without being distracted by system-generated noise.\n\n# Functional Requirements\n\n- The system must hold session state in memory upon connection and initialization without triggering a disk write.\n- Durable persistence to the JSONL session file must be gated until the first meaningful message (user-to-assistant round-trip) is recorded.\n- Session mapping and status tokens must be validated against the active session's origin to prevent cross-session state corruption.\n- Grand Fleet registration must utilize the actual session identifier and generation token instead of generating a separate synthetic ID.\n\n# Acceptance Criteria\n\n- Opening a new session and closing it without sending a message results in zero new files in the session storage directory.\n- The TUI session selector remains free of `(no messages)` entries for all newly created sessions.\n- Multi-instance or parallel agent initializations do not collide or create redundant session shells.\n- Active sessions correctly track their \"dirty\" state and commit to disk only when the significance threshold is met.\n\n#
