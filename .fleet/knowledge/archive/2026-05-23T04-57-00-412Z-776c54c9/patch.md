Overview\n\nfleet-core가 함께 담당하던 인프라 계층 서비스를 host-agnostic 독립 패키지로 분리하여, 오케스트레이션 로직과 인프라 서비스의 패키지 경계를 명확히 합니다. 인프라는 auth storage, data-dir 마이그레이션, detached job 생명주기, log store, settings runtime 등 호스트 환경에 종속되지 않는 기반 서비스를 의미하며, 이를 분리함으로써 오케스트레이션 전용 패키지로서 fleet-core의 책임이 단순화됩니다.\n\n이 결정은 캐리어 페르소나 외부화와 같은 구조적 분리 철학의 연장선상에 있습니다. 코어 패키지가 품고 있던 여러 도메인을 각자의 리프 패키지로 독립시킴으로써, 함대 전체의 패키지 지도에서 \"무엇이 어디에 속하는지\"를 코드를 읽지 않고도 파악할 수 있게 만듭니다.\n\n## Problem\n\n- **패키지 경계 모호성**: 인프라 서비스와 오케스트레이션 로직이 단일 패키지에 공존하여, 어떤 기능이 어떤 계층에 속하는지 시각적으로 구분되지 않았습니다. 새로운 기여자가 코드베이스를 탐색할 때 인프라 유틸리티와 오케스트레이션 프리미티브를 혼동하는 cognitive debt가 반복적으로 발생했습니다.\n- **의존 경로의 비효율**: fleet-agent와 같은 다운스트림 소비자가 인프라 서비스만 필요할 경우에도 전체 fleet-core를 거쳐 간접 접근해야 했습니다. 이는 패키지 의존성 그래프에서 불필요한 중간 노드를 강제하고, 인프라 변경 시 오케스트레이션 계층까지 불필요하게 재빌드되는 blast radius 확대를 초래했습니다.\n- **소유권 구분 불가**: 인프라 변경이 오케스트레이션에 미치는 영향, 그 반대의 영향을 예측하기 어려웠습니다. 코드 리뷰 시 리뷰어가 \"이 변경이 인프라만 touched한 것인지, 아니면 오케스트레이션 계약도 바꾼 것인지\"를 판단하는 데 추가적인 탐색 비용이 들었습니다.\n\n## Goals\n\n- 인프라 서비스를 독립 패키지로 분리하여 오케스트레이션과 인프라의 관심사를 명확히 분리합니다.\n- 다운스트림 소비자가 인프라를 직접 참조하여 의존 경로를 단순화합니다.\n- 인프라 변경의 blast radius를 독립 패키지 경계로 격리합니다.\n- 기존 인프라 API의 서명과 동작을 유지하여 회귀 없이 마이그레이션합니다.\n\n## Non-Goals\n\n- 인프라 서비스 자체의 내부 동작 변경 또는 API 재설계.\n- 오케스트레이션 로직의 내부 아키텍처 변경.\n- 기존 외부 소비자를 위한 별도의 마이그레이션 가이드 문서 작성.\n\n## User Stories\n\n- **As a** 함대 운영자, **when** fleet-agent를 빌드할 때, **then** 전체 오케스트레이션 패키지를 의존성으로 추가하지 않고 인프라 서비스만 직접 참조할 수 있습니다.\n- **As a** 개발자, **when** 인프라 스토리지 로직을 수정할 때, **then** 오케스트레이션 패키지의 테스트나 빌드에 영향을 주지 않고 안전하게 변경할 수 있습니다.\n- **As a** 시스템, **when** 새로운 인프라 서비스를 추가할 때, **then** 오케스트레이션 계층에 대한 지식 없이 인프라 패키지 내부에서만 확장할 수 있습니다.\n- **As a** 기여자, **when** 코드베이스를 처음 탐색할 때, **then** 인프라 유틸리티와 오케스트레이션 프리미티브가 각자의 패키지에 속해 있어 어느 것이 어디에 있는지 직관적으로 파악할 수 있습니다.\n\n## Functional Requirements\n\n- **Host-agnostic 인프라 독립 패키지**: auth storage, data-dir 마이그레이션, detached job 생명주기, log store, settings runtime 등의 기반 서비스를 독립 패키지로 제공합니다.\n- **단방향 의존성**: 오케스트레이션 코드는 인프라 패키지를 사용하되, 인프라 패키지는 오케스트레이션에 대한 어떤 지식도 갖지 않습니다.\n- **다운스트림 직접 접근**: fleet-agent 등 소비자 패키지가 인프라 서비스에 직접 접근할 수 있으며, 이를 위해 오케스트레이션 패키지를 거칠 필요가 없습니다.\n- **동작 보존**: 기존 인프라 API의 서명과 런타임 동작을 그대로 유지하여, 마이그레이션 후에도 기존 소비자가 감지할 수 있는 차이가 없어야 합니다.\n\n## Acceptance Criteria\n\n- [ ] 인프라 독립 패키지가 워크스페이스에 등록되어 빌드 및 테스트되는가?\n- [ ] 오케스트레이션 패키지가 인프라 패키지를 import하여 기존 동작을 유지하는가?\n- [ ] 다운스트림 소비자가 인프라 패키지를 직접 import하여 기존 간접 접근을 대체하는가?\n- [ ] 기존 인프라 API의 서명과 동작이 회귀 없이 유지되는가?\n- [ ] 인프라 변경 시 오케스트레이션 패키지의 테스트가 영향받지 않는가?\n\n## Open Questions\n\n- 없음. 아키텍처 방향은 확정되었으며, 구현이 완료되어 출하됨.\n\n## Related\n\n- [[wiki:prd-carrier-persona-extraction]] — 구조적 분리
