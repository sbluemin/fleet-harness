{"id":"prd-tui-mission-control","title":"PRD: 전용 CLI Mission Control 도입","tags":["fleet-tui","fleet-agent","dedicated-cli","mission-control","region-stack","ux"],"created":"2026-05-24T11:19:54.420Z","updated":"2026-05-24T11:19:54.420Z","version":1,"templateId":"prd","body":"## Overview\n\nMission Control은 Claude와 Codex를 1급 CLI로 실행하되, 화면의 소유권은 Fleet이 가진다는 전용 미션 콘솔 경험이다. 사용자는 Claude와 Codex의 원래 인터랙티브 CLI를 그대로 사용하지만, 그 주변의 생명주기, 상태 표시, transcript, 종료 후 행동은 Fleet의 미션 컨트롤이 책임진다. MVP는 raw PTY를 첫 화면으로 노출하는 방식에서 벗어나, CLI 실행, 활성 세션 표시, 종료 상태 설명, 다음 행동 제안을 모두 Fleet이 정의한 상위 화면 안에서 제공한다.\n\n## Problem\n\n사용자가 Claude 또는 Codex 전용 CLI에서 지원되는 종료 명령을 입력하면 하위 프로세스가 종료되고, dedicated 영역은 비어 있거나 복구 불가능한 화면처럼 남을 수 있다. 이는 정상적인 사용자 행동을 제품 오류처럼 보이게 만든다. 또한 Fleet이 여러 CLI 캐리어를 지휘하는 미션 컨트롤이라는 제품 약속보다 하위 프로세스에 종속된 화면처럼 보이게 한다.\n\n사용자는 Claude와 Codex를 1급 CLI로 계속 사용해야 한다. 동시에 해당 CLI 프로세스가 자연스럽게 종료되더라도 Fleet은 사용자의 방향감, 의도, 복구 행동을 보존해야 한다.\n\n## Goals\n\n- Fleet이 소유하는 Mission Control 화면을 dedicated CLI 작업의 지속적인 표시 표면으로 만든다.\n- Claude와 Codex를 해당 표면 안에서 실행되는 1급 인터랙티브 CLI로 유지한다.\n- 프로세스 종료를 빈 화면이 아니라 명시적인 사용자 상태 전환으로 처리한다.\n- 재실행, transcript 확인, provider 전환, 새 미션 시작을 위한 MVP 경로를 제공한다.\n- Mission Control을 raw terminal panel이 아니라 작전 콘솔로 설명하는 제품 언어를 정립한다.\n\n## Non-Goals\n\n- 하위 프로세스가 종료된 뒤 기존 PTY가 실제로 부활한다고 약속하지 않는다.\n- 활성 세션 중 Claude와 Codex의 원래 CLI 인터랙션 모델을 숨기거나 대체하지 않는다.\n- MVP에서 다중 provider 미션 handoff 자동화를 구현하지 않는다.\n- 영구 클라우드 동기화나 기기 간 세션 복구를 요구하지 않는다.\n- Fleet TUI 전체 내비게이션 모델을 MVP 범위에서 재설계하지 않는다.\n\n## User Stories\n\n- 사용자로서, 내가 어떤 CLI 캐리어를 운용하는지 알 수 있도록 Fleet이 소유한 콘솔에서 Claude 또는 Codex를 실행하고 싶다.\n- 사용자로서, 활성 CLI가 제약된 폼이나 래퍼가 아니라 원래의 1급 CLI처럼 느껴지길 원한다.\n- 사용자로서, CLI를 종료했을 때 프로세스가 의도적으로 끝났고 다음에 무엇을 할 수 있는지 명확히 알고 싶다.\n- 사용자로서, 종료 후 이전 transcript를 확인해 미션 맥락을 유지하고 싶다.\n- 사용자로서, 방향감을 잃지 않고 같은 CLI를 다시 실행하거나 다른 지원 CLI로 전환하고 싶다.\n\n## Functional Requirements\n\n- dedicated CLI 영역은 하위 CLI를 실행하기 전에 Fleet이 소유한 Mission Control 홈 상태를 표시한다.\n- Mission Control 홈 상태는 Claude와 Codex가 모두 사용 가능할 때 최소한 두 CLI 중 하나를 선택할 수 있게 한다.\n- CLI가 활성화되면 Mission Control은 활성 프로세스에 완전한 인터랙티브 포커스를 제공하되, Fleet 소유의 상태 표시 또는 복귀 가능한 내비게이션 단서를 유지한다.\n- 활성 프로세스가 정상 종료되면 Mission Control은 활성 화면을 종료 상태 화면으로 전환한다.\n- 활성 프로세스가 비정상 종료되면 Mission Control은 안전한 다음 행동을 포함한 별도의 실패 상태를 표시한다.\n- 종료 상태 화면은 재실행, transcript 확인, provider 전환, 닫기 행동을 제공한다.\n- transcript 확인 상태는 이전 세션 출력을 읽기 전용 맥락으로 보존한다.\n- 제품 문구는 프로세스 종료 후 기존 PTY를 resume할 수 있다고 주장하지 않는다.\n- MVP는 active, ended, failed, idle 상태에 대한 명확한 사용자 표시명을 정의한다.\n- 지원 CLI를 사용할 수 없는 경우에도 Mission Control은 설명 가능한 unavailable 상태를 표시해야 한다.\n\n## Acceptance Criteria\n\n- 활성 Claude 또는 Codex CLI에서 종료해도 dedicated 영역이 빈 화면으로 남지 않는다.\n- 정상 종료 후 사용자는 최소한 재실행, transcript 확인, 닫기 행동이 포함된 명시적인 종료 상태를 본다.\n- 재실행은 기존 PTY 부활이 아니라 새로운 CLI 프로세스 시작으로 표현된다.\n- 활성 CLI는 실행 중 원래의 인터랙티브 CLI로 사용할 수 있다.\n- MVP는 정상적인 사용자 종료와 예기치 못한 종료를 사용자 문구에서 구분한다.\n- 이전 세션 transcript는 현재 Fleet 세션 안에서 종료 상태 화면을 통해 접근 가능하다.\n- 홈 상태는 Fleet이 콘솔을 소유하고 Claude/Codex는 그 안에서 실행되는 도구임을 전달한다.\n- 제품 이름과 문구는 Mission Control 언어를 일관되게 사용한다.\n\n## Open Questions\n\n- 정상 종료 후 기본 행동은 같은 CLI 재실행, 홈으로 복귀, transcript 확인 중 무엇이어야 하는가?\n- MVP에서 transcript를 얼마나 보존해야 하며, 애플리케이션 재시작 이후에도 유지해야 하는가?\n- 종료 후 provider 전환은 선택적 미션 맥락 주입을 포함해야 하는가, 아니면 MVP에서는 단순 새 실행으로 제한해야 하는가?\n- Claude 또는 Codex가 설치되어 있지 않거나 실행할 수 없을 때 어떤 unavailable 상태 문구를 표시해야 하는가?\n- 활성 CLI 입력을 방해하지 않으면서 Fleet 소유의 Mission Control 컨트롤로 돌아가는 단축키는 무엇이어야 하는가?\n\n## Related\n\n- [[wiki:guide-001-fleet-harness-overview]] — Fleet의 미션 컨트롤 관점과
