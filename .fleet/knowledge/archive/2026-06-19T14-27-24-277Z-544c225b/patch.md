{"id":"guide-008-development-release-workflow","title":"Guide - 008 Development & Release Workflow","tags":["guide","changelog","release","ci","workflow","contributing"],"created":"2026-06-19T14:27:24.277Z","updated":"2026-06-19T14:27:24.277Z","version":1,"body":"---\nid: guide-008-development-release-workflow\ntitle: Guide - 008 Development & Release Workflow\ntags:\n  - guide\n  - changelog\n  - release\n  - ci\n  - workflow\n  - contributing\ncreated: 2026-06-19\nupdated: 2026-06-19\nversion: 1\ntemplate_id: freestyle\n---\n\n# Development & Release Workflow\n\n이 문서는 fleet-harness의 브랜치 전략부터 PR, changelog 작성, 릴리스, npm publish까지 전체 개발·배포 워크플로우를 정리한다. 주요 목표는 다음과 같다.\n\n- 모든 PR은 `canary`를 거쳐 통합된다.\n- 릴리스에 영향을 주는 변경은 PR 시점에 `.changelog.d/*.md` 조각(fragment)으로 기록한다.\n- 릴리스는 `main` 브랜치 푸시가 트리거하는 CI가 자동으로 수행하며, 수동으로도 동일한 컴파일러로 미리 검증할 수 있다.\n- 9개 워크스페이스 패키지는 통합 단일 버전으로 관리하고, 실제 npm publish 대상은 `fleet-cli`와 `fleet-console` 2개뿐이다.\n- 별도의 changeset 도구([@changesets/cli](https://github.com/changesets/changesets) 등)는 사용하지 않는다.\n\n## 브랜치 전략\n\n| 브랜치 | 역할 | 비고 |\n|---|---|---|\n| `canary` | 통합용 기본 base 브랜치 | 모든 PR의 target은 `canary`여야 함 |\n| `main` | 릴리스 채널 | `stable-release.yml`이 `push` 이벤트로 트리거됨 |\n\n`.github/workflows/pr-target-guard.yml`은 `pull_request_target` 이벤트로 동작하여 `canary`가 아닌 base를 가진 PR을 자동으로 코멘트와 함께 close한다. fork 저장소에서 별도의 base 변경이 어려운 경우에는 `canary`를 target으로 새 PR을 열어야 한다.\n\n`main`에 코드 변경이 push되면 `.github/workflows/stable-release.yml`이 실행된다. 단, 문서·플랜·CI 설정·마크다운 등 비배포 경로(`docs/**`, `.fleet/**`, `.github/**`, `.claude/**`, `.agents/**`, `.codex/**`, `**.md`)만 변경된 push는 릴리스를 트리거하지 않는다.\n\n## PR 워크플로우\n\n### 1. Conventional Commits 제목 검증\n\n`.github/workflows/pr-title.yml`이 PR 제목을 검증한다. 허용되는 형식은 다음과 같다.\n\n```text\ntype(scope): summary\ntype!: summary\ntype(scope)!: summary\n```\n\n허용 type은 `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`이다.\n\n### 2. Changelog fragment 게이트\n\n`.github/workflows/changelog-fragment.yml`은 PR에 `.changelog.d/*.md` 조각이 포함되었는지, 또는 `no-changelog` 라벨이 달려 있는지 검사한다.\n\n- `merge-base`에서 `HEAD`까지의 diff로 실제 PR이 추가/수정한 파일만 본다.\n- `.changelog.d/*.md` 파일이 하나 이상 있으면 통과한다.\n- `no-changelog` 라벨이 있으면 조각을 요구하지 않는다.\n- 조각이 있을 경우 `node scripts/compile-changelog-fragments.mjs --check --allow-empty`로 형식을 추가 검증한다.\n\n`.github/PULL_REQUEST_TEMPLATE.md`과 `.fleet/skills/pr-workflow/SKILL.md`에도 동일한 기대가 명시되어 있어, PR 작성자가 조각 추가를 누락하지 않도록 한다.\n\n## CHANGELOG 조각 작성 규칙\n\n### 저장 위치와 원칙\n\n- 미발행 릴리스 노트는 `.changelog.d/*.md`에 PR마다 별도의 파일로 저장한다.\n- `CHANGELOG.md`의 `[Unreleased]` 섹션은 항상 비어 있어야 한다. 수동으로 내용을 추가하거나 수정하지 않는다.\n- `.changelog.d/` 디렉토리에는 `.gitkeep`과 조각 파일만 둔다. `README.md` 등 추가 문서는 두지 않는다.\n\n### 파일 형식\n\n각 조각은 YAML frontmatter와 bullet 본문으로 구성된다.\n\n```markdown\n---\nsection: Added\n---\n- [fleet-console] Fleet Console adds a Model Sign-in section ...\n```\n\n- `section`은 `Added`, `Changed`, `Fixed`, `Removed`, `Breaking Changes` 중 하나여야 한다.\n- 본문은 `- `로 시작하는 bullet 목록만 허용한다.\n- 각 bullet은 허용된 패키지 태그 하나 이상으로 시작해야 한다.\n\n### 허용 package tag vocabulary\n\n조각 bullet의 패키지 태그는 다음 8개만 사용할 수 있다.\n\n- `[core-agent]`\n- `[core-unified-agent]`\n- `[fleet-infra]`\n- `[fleet-admiral]`\n- `[fleet-carriers]`\n- `[fleet-wiki]`\n- `[fleet-console]`\n- `[fleet-cli]`\n\n사용 금지(retired) 태그: `[core]`, `[wiki]`, `[wiki-web]`, `[agent-core]`, `[unified-agent]`, `[mcp-server]`, `[agent]`, `[carriers]`.\n\n또한 `@dotobokuri/` scope를 태그에 포함해서는 안 된다. 여러 패키지에 영향을 주는 경우 태그를 조합할 수 있다(예: `[fleet-cli][fleet-console]`).\n\n### 항목 작성 가이드\n\n- 한 항목은 사용자/운영자 관점에서 한 줄로 요약한다.\n- 소스 파일 이름, 함수 이름, 줄 번호, 구현 세부사항은 적지 않는다.\n- 모든 bullet은 영어(ASCII)로 작성한다.\n\n## 릴리스 절차\n\n### 자동 릴리스 파이프라인\n\n`.github/workflows/stable-release.yml`은 `main` push 시 다음을 수행한다.\n\n1. **중복 실행 방지**: 마지막 커밋 메시지가 `chore(release):`로 시작하면 건너뛴다.\n2. **버전 결정**: 최신 `v*` 태그 이후 커밋에서 `feat` type이 있으면 minor, 없으면 patch를 올린다.\n3. **버전 갱신**: 루트 및 모든 워크스페이스 `package.json`의 `version` 필드를 정규식 치환으로 동일 버전으로 갱신한다.\n4. **CHANGELOG 컴파일**: `node scripts/compile-changelog-fragments.mjs --version <version> --date <YYYY-MM-DD> --allow-empty`를 실행하여 `[Unreleased]` 아래에 새 버전 섹션을 추가하고, 사용된 조각 파일은 삭제한다.\n5. **버전 동기화 검증**: 모든 tracked `package.json`이 동일 버전인지 JSON parse로 확인한다.\n6. **빌드 및 publish**: `fleet-console`과 `fleet-cli`를 각각 `scripts/publish-fleet-*.mjs`로 npm에 배포한다.\n7. **릴리스 커밋**: `CHANGELOG.md`, `.changelog.d`, 모든 `package.json`을 스테이징하여 `chore(release): v<version>` 커밋을 `main`에 push한다.\n8. **태그 및 GitHub Release**: `v<version>` 태그를 만들고, `CHANGELOG.md`에서 해당 버전 섹션을 추출한 release notes로 GitHub Release를 생성한다.\n\n### 로컬 릴리스 준비\n\n`.fleet/skills/release-version-update/SKILL.md`은 로컬에서 릴리스를 준비할 때 따르는 절차를 정의한다.\n\n1. `AGENTS.md`를 읽고 현재 브랜치/작업 트리를 확인한다.\n2. `main`과의 diff를 요약하여 릴리스 영향 범위를 파악한다.\n3. target version을 결정한다.\n4. 루트 `package.json`과 `pnpm-lock.yaml`의 버전을 갱신한다.\n5. 조각을 검증하고 preview한 뒤, `compile-changelog-fragments.mjs`로 `CHANGELOG.md`에 기록한다.\n\n컴파일러는 `compile-changelog-fragments.mjs` 단일 스크립트이며, 다음 모드를 지원한다.\n\n```bash\n# 형식 검증\nnode scripts/compile-changelog-fragments.mjs --check\n\n# 릴리스 섹션 preview\nnode scripts/compile-changelog-fragments.mjs --dry-run --version 1.9.0 --date 2026-06-19\n\n# CHANGELOG.md에 실제 기록하고 조각 삭제\nnode scripts/compile-changelog-fragments.mjs --version 1.9.0 --date 2026-06-19\n```\n\n`--allow-empty` 옵션은 의도적인 no-changelog 릴리스에만 사용한다.\n\n## 버전·publish 전략\n\n### 통합 단일 버전\n\nfleet-harness의 9개 package.json(루트 1개 + 워크스페이스 8개)은 항상 동일한 버전을 사용한다. `stable-release.yml`은 정규식으로 모든 tracked `package.json`의 `version` 필드를 한 번에 갱신하고, 별도의 검증 스텝에서 JSON parse로 일치 여부를 확인한다. 패키지별 독립 버전은 사용하지 않는다.\n\n### publish 대상\n\n실제 npm publish는 다음 2개 패키지만 대상으로 한다.\n\n- `@dotobokuri/fleet-console`\n- `@dotobokuri/fleet-cli`\n\n나머지 6개 워크스페이스 패키지는 `private: true`로 유지되며, `tsup`의 `noExternal: [/^@dotobokuri\\//]` 설정으로 번들에 인라인되어 publish 산출물에 흡수된다.\n\n### publish helper\n\n`scripts/publish-fleet-console.mjs`, `scripts/publish-fleet-cli.mjs`, `scripts/pack-fleet-console-manifest.mjs`는 릴리스 파이프라인에서 불변(invariant)이다. 이 스크립트들은:\n\n- `private` 필드를 제거하고,\n- `workspace:*` 의존성을 제거한 뒤 외부 의존성만 남기며,\n- `scripts`를 `postinstall`만 남기고 교체하고,\n- publish 후 원본 `package.json`을 복원한다.\n\n`fleet-console`은 `node-pty`와 `ws`를 external로 유지하고, `fleet-cli`는 `@clack/prompts`, `@xterm/headless`, `node-pty`와 `@dotobokuri/fleet-console`을 external로 유지한다.\n\n## 중요 제약\n\n- **@changesets 미사용**: 별도의 changeset 관리 도구를 도입하지 않는다. 자체 제작한 `compile-changelog-fragments.mjs`로 towncrier-style 경량 방식을 사용한다.\n- **publish helper 불변**: 릴리스 자동화를 수정할 때 3개 publish helper의 동작은 변경하지 않는다.\n- **CHANGELOG.md [Unreleased] 수동 편집 금지**: 모든 미발행 내용은 `.changelog.d/*.md` 조각으로 관리한다.\n- **PR base는 canary**: `main`이나 `master`로 직접 PR을 열면 자동으로 close된다.\n\n## 관련 파일 및 스킬\n\n- `.github/workflows/stable-release.yml` — 릴리스 자동화\n- `.github/workflows/changelog-fragment.yml` — PR changelog 조각 게이트\n- `.github/workflows/pr-title.yml` — Conventional Commits 제목 검증\n- `.github/workflows/pr-target-guard.yml` — non-canary PR 차단\n- `scripts/compile-changelog-fragments.mjs` — 무의존 조각 컴파일러\n- `scripts/publish-fleet-cli.mjs`, `scripts/publish-fleet-console.mjs`, `scripts/pack-fleet-console-manifest.mjs` — publish helper\n- `.fleet/skills/release-version-update/SKILL.md` — 로컬 릴리스 준비 스킬\n- `.fleet/skills/pr-workflow/SKILL.md` — PR 작성에서 merge까지의 스킬\n- `.github/PULL_REQUEST_TEMPLATE.md` — PR 본문 템플릿\n- `AGENTS.md` — Changelog
