Fleet TUI는 외부 터미널의 키보드 프로토콜을 직접 제어하고, 호스트 키바인딩 레지스트리를 입력 라우팅 계층에 배치하는 아키텍처를 확립했다. 이 결정은 다중 자식 프로세스가 동시에 활성화된 터미널 환경에서 발생하는 프로토콜 상태 충돌, 키 입력 무단 가로채기, 정규화 오류 등의 인지 부채를 해소하기 위해 남겨졌다.

이전에는 프로토콜 상태 추적의 복잡성, 키 입력 충돌 위험, 이중 갱신 지점, 도메인 경계 혼란 등의 마찰이 지속적으로 발생했다. 이러한 마찰의 구조적 원인은 책임 분리 원칙의 미확립이었다. 터미널 키보드 프로토콜은 TUI 엔진의 입력 표면에 속하는데, 이를 자식 프로세스에게 위임하려는 시도는 누가 외부 터미널을 제어하는가라는 근본 질문에 대한 답을 회피한 것이었다. 키 입력 정규화 범위를 전역으로 확대하려는 접근은 어떤 키 시퀀스가 호스트용이고 어떤 것이 자식용인가를 구분하지 않은 결과였다. keybinding 정의를 인프라 패키지에 두려는 시도는 도메인 정책을 host-agnostic 인프라에 밀어넣는 도메인 경계 침범이었다. 두 가지 표현 형식을 독립적으로 관리하는 방식은 단축키의 의미는 하나인데 표현은 두 개라는 사실을 데이터 모델에 반영하지 못한 설계 결함이었다.

결정의 목표는 프로토콜 상태 일관성 확보, 키 입력 충돌 방지, 단축키 정의의 Single Source of Truth 확립, 도메인 경계 명료화이다. Non-Goals로는 외부 터미널 표준 변경, 전용 CLI 내부 해석 동작 변경, 새 표준 도입, TUI 외 입력 표면 확장이 있다.

사용자 스토리는 운영자가 다중 자식 프로세스 환경에서 충돌 없이 사용하고, 기여자가 단축키 추가 시 하나의 지점만 갱신하며, 코드 탐색 시 책임 분리가 명확하고, tmux 환경에서 확장 키가 정상 작동하는 것이다.

기능 요구사항은 TUI가 키보드 확장 모드를 직접 제어하고, 이중 프로토콜을 동시 활성화하며, 선택적 정규화를 적용하고, keybinding 레지스트리를 TUI 입력 계층에 배치하며, 도메인 정의를 host assembly 지점에 두고, 대응 맵을 자동 파생하는 것이다.

수용 기준은 직접 검증 가능한 체크리스트로 구성된다.

결정은 tmux 호환성, 전용 CLI 입력 보존, Composition Root 원칙, SSoT 엄수라는 제약 하에 내려졌으며, 자식 프로세스 proxy, kitty push only, broad normalization, 인프라 계층 레지스트리, 인프라 계층 기본 단축키, 하드코딩된 이중 대응 맵 등의 대안은 거부되었다.
