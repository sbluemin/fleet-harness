It consolidates what was previously five separate files into one module organized by labelled `#region` sections.\n\n## Why a Single File\n\nThe previous layout (`provider-stream.ts`, `provider-runtime.ts`, `provider-guard.ts`, `provider-guard-command.ts`, `thinking-level-patch.ts`) split closely related responsibilities — all of which depend on the same `@mariozechner/pi-ai` and `@mariozechner/pi-coding-agent` imports — across files that imported each other in a tangled web. Consolidating into one file with regions:\n\n- Enforces the \"single Pi-AI gateway\" rule mechanically: the rule is \"this file is the only `pi-ai` importer,\" which is trivial to grep.\n- Removes cross-file imports that were really a single module's internals.\n- Keeps each Pi-runtime concern visible at a glance.\n- Simplifies the consumer-side import surface: every Pi-side caller imports from `./provider.js` regardless of which concern they need.\n\n## Region Layout\n\n```\n═══════════════════════════════════════════════════════════════════════════\n#region pi-ai gateway (re-export)\n═══════════════════════════════════════════════════════════════════════════\n  - Every other adapter consumes the gateway through exported bridge functions.\n2. **No re-fragmentation**: do not split `provider.ts` back into the legacy multi-file layout. Region headers are the architecture, not a refactor target.\n3. **No host-side fleet-core duplication**: prompt assembly, tool spec definitions, session pool/drift logic, and MCP routing belong to fleet-core.
