{"id":"field-manual-large-refactor-cycle","title":"Field Manual — Large Refactor Cycle (Vanguard → Nimitz → Kirov → Ohio → Sentinel)","body":"# Field Manual — Large Refactor Cycle\n\nFor non-trivial refactors that touch multiple packages, a five-stage carrier delegation cycle has proven effective. Both the admiral.agent migration and the legacy agent-runtime.ts removal followed this pattern with consistent quality outcomes.\n\n## The Cycle\n\n```\nVanguard (정찰) → Nimitz (검증) → Kirov (계획) → Ohio (실행) → Sentinel (검증)\n```\n\nEach stage produces an artifact that the next stage consumes. Skipping stages or compressing them into one carrier consistently produces lower-quality work and higher rework cost.\n\n## Stage 1 — Vanguard: Reconnaissance\n\n**Purpose**: enumerate the surface area of the change. Identify call sites, classify types, map dependencies.\n\n**Inputs**: a goal statement (e.g., \"remove legacy `_shared/agent-runtime.ts`\").\n\n**Outputs**:\n- list of every consumer (file:line)\n- type/symbol classification matrix (duplicate / SSoT / dead / new home)\n- preliminary risk inventory\n\n**Anti-pattern**: skipping reconnaissance and going straight to planning. Plans built on guessed call-site lists drift mid-execution and trigger plan rewrites.\n\n## Stage 2 — Nimitz: Architecture Validation\n\n**Purpose**: pressure-test the proposed shape against the recon data. Decide tradeoffs that the planner cannot decide alone.\n\n**Inputs**: Vanguard's recon report + a strawman of the target architecture.\n\n**Outputs**:\n- explicit option comparison (e.g., \"merge into session.ts vs. new executor.ts vs. shared internal layer\")\n- chosen option with rationale tied to recon evidence\n- additional fixed constraints to add to the plan\n\n**Anti-pattern**: letting Kirov pick the architecture. Kirov optimizes for executable steps, not architectural soundness. Forcing Kirov to do both produces plans that are detailed but pointed at the wrong target.\n\n## Stage 3 — Kirov: Plan File\n\n**Purpose**: produce a single artifact (`.fleet/plans/<topic>.md`) that contains every decision needed for Ohio to execute without further questions.\n\n**Inputs**: Nimitz's architecture decision + accumulated fixed constraints (e.g., 44 numbered constraints across both refactors).\n\n**Outputs**: a plan file with:\n- Goal + Scope IN/OUT\n- Architecture Decisions (numbered, immutable during execution)\n- Type Migration Matrix or equivalent enumeration\n- File Ownership (which package/path owns what after)\n- Wave A/B/C/... breakdown (each wave has Files / Steps / Acceptance / Risk & Rollback)\n- QA Gates + Static Grep Checks\n- Acceptance Criteria\n- Cross-Wave Invariants\n- Glossary\n- Admiral Direction Needed (open questions, if any)\n\n**Anti-pattern**: writing the plan and the code in the same carrier. Plans degrade into running commentary and lose the \"Ohio can execute this without me\" property.\n\n## Stage 4 — Ohio: Wave-by-Wave Execution\n\n**Purpose**: implement one wave per sortie. Each wave is independently buildable and testable.\n\n**Inputs**: the plan file's Wave N section + accumulated constraints.\n\n**Outputs per wave**:\n- enumerated file changes (created/modified/deleted)\n- typecheck/build/test results\n- static grep verification\n- explicit deviation report if the plan was off\n\n**Wave granularity heuristic**: each wave should compile/test independently. Splitting too coarsely creates rollback hazards; splitting too finely creates merge churn.\n\n**Anti-pattern**: parallel waves. Wave dependencies are usually subtle (e.g., legacy import paths still alive in Wave A but expected gone in Wave C). Sequential execution is cheaper than debugging an interleaved failure.\n\n## Stage 5 — Sentinel: Final Regression Audit\n\n**Purpose**: independent quality gate. Sentinel does not see Ohio's reasoning; it only sees the final tree against the plan's acceptance criteria.\n\n**Inputs**: the plan file's Acceptance Criteria + the final source tree.\n\n**Outputs**: a verdict (PASS / PASS WITH WARNING / WARNING / FAIL) with:\n- evidence for each acceptance criterion (file:line)\n- grep gate results\n- Cross-Wave Invariant verification\n- severity-classified deviations (Critical / High / Medium / Low)\n- recommended commit/PR posture\n\n**Anti-pattern**: letting Ohio self-verify. Self-verification produces tunnel-vision PASSes. Sentinel routinely surfaces deviations Ohio missed (e.g., subpath references in `package.json` after a file deletion).\n\n## When to Use the Full Cycle\n\nThe cycle is overkill for:\n\n- Single-file edits\n- Bug fixes whose scope is already identified\n- Documentation-only changes\n- Test additions for existing behavior\n\nThe cycle pays off when:\n\n- The change spans multiple packages\n- Public APIs change\n- Type signatures migrate\n- Legacy code is being retired\n- The work involves more than ~6 files\n\n## Empirical Outcomes\n\n- **admiral.agent migration**: Vanguard 5-fan-out + Nimitz 3-round (Q1–Q9 over three sorties) + Kirov 1 plan + Ohio Wave A/B/C + Sentinel 3 rounds (1 FAIL → D-Fix → PASS WITH WARNING → D-Fix-2 → PASS). 5000+ lines refactored. Deviations caught by Sentinel saved at least one production-impacting `null` API path.\n\n- **agent-runtime removal**: Vanguard 1 fan-out (type matrix) + Nimitz 1 round + Kirov 1 plan + Ohio Wave A/B/C + Sentinel 1 round (PASS WITH WARNING). 1500-line legacy module deleted; 911 insertions / 2085 deletions net.\n\nIn both cases, **fixing issues during execution required revisiting the recon stage**, not the planning stage.
