NEVER ...` 또는 `MUST ...` 패턴으로 통일.\n- **소문자 must 금지**: 강조 의도라면 `MUST` 대문자.\n\n## 적용 예시\n\n### Permissions (안전 invariant + binding 의무 혼합)\n```ts\npermissions: [\n  \"CRITICAL: Strictly read-only. NEVER delegate code modification or file editing to this carrier.\",\n  \"CRITICAL: NEVER sortie Nimitz without prior reconnaissance — sortie vanguard/tempest FIRST.\",\n  \"Full access to read the codebase and execute read-only commands for analysis.\",\n  \"MUST NOT decompose work into task waves, delivery schedules, or implementation checklists — handoff belongs to Kirov.\",\n],\n```\n\n### Principles (binding 행동 원칙)\n```ts\nprinciples: [\n  \"MUST treat the Admiral's <objective>, <scope>, <constraints>, and <references> as binding design contracts.\",\n  \"If an alternative design seems superior, MUST complete the assigned work AS-INSTRUCTED first, then report the alternative ONLY as a follow-up suggestion. NEVER substitute the alternative silently.\",\n],\n```\n\n## 적용 대상\n\n이 사다리는 다음 metadata 필드에 적용한다:\n- `permissions[]` — 가장 적극적으로\n- `principles[]` — binding 의무에 한해\n- `whenToUse[]` / `whenNotToUse[]` / `outputFormat` — 강조 미사용\n\n## 새 carrier 추가 절차\n\n1. carrier 분류 결정 (전략/판단 vs 정찰/인사이트 vs 실행 일꾼) — 별도 wiki \"Carrier 자율성 vs Binding 매트릭스\" 참고\n2. 분류에 따라 binding 강도 선택\n3. 본 사다리에 따라 표현 일관화\n4. 8개 기존 carrier (Genesis, Ohio, Chronicle, Nimitz, Sentinel, Kirov, Vanguard, Tempest) 와 톤 비교 검증","tags":["carrier","metadata","doctrine","prompt-design","consistency"],"created":"2026-05-04T10:30:25.872Z","updated":"2026-05-04T10:30:25.872Z","version":1,"rawSourceRef":"raw/2026-05-04-carrier-metadata-emphasis-ladder-source.md"}
