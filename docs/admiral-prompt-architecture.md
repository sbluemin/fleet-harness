## 1. Purpose

This document is the operational reference for the Admiral's prompt assembly and
runtime lifecycle model. The current architecture has no per-turn runtime-context
tag prefix. The Admiral system prompt is assembled by fleet-admiral, and live
protocol/carrier/job state is consumed by runtime services, UI, and tools through
the `@sbluemin/fleet-admiral` root-barrel facades.

This document is for the Admiral. It is not a public spec, not a contributor
guide, and not a Chronicle-managed asset.

---

## 2. System Prompt Shape

`buildSystemPrompt()` in `packages/fleet-admiral/src/prompts.ts` assembles the
Admiral prompt. The static prompt includes:

- `FLEET_PREAMBLE`
- `RISEN_DEV_SLATE` when `bootMode === "dev"`
- `<fleet section="role">` outside dev mode
- `<fleet section="roster">` when carriers are registered
- `<fleet section="protocols">` with the protocol catalog
- `<fleet section="standing-orders">`
- one `<fleet section="tool-guide" tool="...">` block per registered tool

The prompt does **not** teach request-time tags for active protocol or taskforce
availability. The removed tags are not generated by the Admiral prompt path.

`buildFleetAcpSystemPrompt()` in `packages/fleet-admiralty/src/prompts.ts`
builds the Fleet ACP prompt. It also does not include a runtime-context tag
section.

---

## 3. Live State Access

Runtime state is read through fleet-admiral facades:

- `admiral.protocols.getActiveProtocol()`
- `admiral.carrier.getRegisteredOrder()`
- `admiral.carrier.getActiveTaskForceIds()`
- `admiral.store.*`
- `admiral.carrierJobs.*`

Host-agnostic job infrastructure is read through `@sbluemin/fleet-infra/job`.

These values are operational inputs for services, overlays, tools, and status
rendering. They are not serialized into a per-turn prompt wrapper.

---

## 4. Lifecycle Boot

`bootFleetAdmiral(options)` in `packages/fleet-admiral/src/runtime.ts` is the
lifecycle boot entry point. It performs boot side effects and returns only a
shutdown handle:

```ts
interface FleetAdmiralShutdownHandle {
  shutdown(): Promise<void>;
}
```

Consumers use root-barrel facades such as `admiral` and `admiralty` directly.
Infra consumers import from `@sbluemin/fleet-infra`. The boot function does not
return a domain service container.

`packages/fleet-agent/src/runtime/runtime.ts` owns the shutdown handle in module
scope. `bootRuntime()` starts fleet-admiral and reconciles host runtime state.
`shutdownRuntime()` is the only fleet-agent path that invokes the handle.

---

## 5. Executor Path

Carrier execution is routed through `admiral.agent.executor.executeWithPool()` and
`admiral.agent.executor.executeOneShot()`. Carrier requests receive the request
body composed by the caller plus the carrier system prompt assembled by
`buildCarrierSystemPrompt()`.

Executor sessions receive their allowed MCP tools at connect time. They do not
receive hidden runtime-context prompt tags.

---

## 6. Carrier Completion Channel

`[carrier:result]` notifications are a separate `<system-reminder
source="carrier-completion">` channel. They are produced from carrier job stream
events and forwarded by the host so the Admiral can retrieve the archived result
with `carrier_jobs(action:"result", format:"full")` when needed.

This channel is not a per-turn runtime-context prompt.

---

## 7. Known Limits

| Limit | Effect |
|-------|--------|
| System prompt content is session-scoped | Prompt changes require reconnect or a new session. |
| Protocol catalog is embedded statically | Active protocol state is read by services and UI through facades. |
| Executor path has no hidden runtime tags | If a carrier needs state, the Admiral must include it in the request. |
| Fleet-admiral boot is lifecycle-only | Consumers must use root-barrel facades for domain operations. |
