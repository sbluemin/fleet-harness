# Fleet 지침 유지보수

`CLAUDE.md`, 작업 스킬, 그 참조 문서를 개편할 때 사용하는 문서다. 일반 구현 작업의 필수 사전 읽기 목록이 아니다.

## 적용 근거

2026-09-05의 [Rethinking Skills and AGENTS.md for GPT-6 Astra: A Practical Guide](https://www.explainx.ai/blog/gpt-6-astra-skills-agents-md-prompting-guide-2026)를 다음처럼 적용한다.

| 가이드의 제안 | Fleet에서의 적용 |
|---|---|
| 상시 문맥과 무조건적인 사전 읽기를 줄인다 | 루트는 소유권·위험 경계와 작업별 참조를 제공한다. 하위 지침은 해당 경로에 적용한다. |
| 스킬을 구체적인 사용 사례로 분리한다 | description은 언제 사용하고 언제 사용하지 않는지 식별할 수 있게 한다. 본문은 진입점으로 두고 상세 절차·자료는 필요할 때 읽는다. |
| 구형 모델에 맞춘 과도한 실행 순서를 재평가한다 | 목표·입출력·완료 조건을 남긴다. 순서가 안전성이나 결과를 바꾸는 절차는 보존한다. |
| 낮은 위험의 연속 작업을 명시적으로 허용한다 | 승인 범위 안의 로컬 수정·관련 검사·자체 회귀 수정은 중간 재가 없이 진행한다. 외부 게시·배포·파괴적 작업의 권한은 별개다. |
| 검증 범위와 종료 조건을 명확히 한다 | 변경 경계에 맞는 증거로 완료를 판정한다. 전역 테스트의 반복도, 검증 자체의 삭제도 기본값으로 삼지 않는다. |

이 글은 외부 2차 해설과 사례를 제공하며, 모델 간 효과를 입증하는 통제 실험은 제시하지 않는다. 특정 모델이 알아서 검증한다거나 더 신뢰할 수 있다는 주장은 보안·승인·검증 제약을 제거할 근거로 사용하지 않는다. Fleet 지침은 여러 Agent CLI와 모델에 공통으로 적용한다.

## 어디에 남길 것인가

- **`CLAUDE.md`**: 정상 탐색으로는 작업 전에 발견하기 어렵고, 위반 비용이 크며, 안정적으로 유지되는 경계. 가장 가까운 소유 스코프에 둔다. 생성물과 원본의 경계를 알려 주는 파일 포인터는 필요한 예외다.
- **스킬**: 특정 작업에서만 필요한 반복 실행 절차. description만으로 선택할 수 있게 하고 중첩된 catch-all 스킬은 합치거나 배타적인 작업 경계로 나눈다. 이미 harness가 제공하는 도구 계약을 복사하지 않는다.
- **참조 문서**: 설계 근거, 상세 설명, 사례, 드물게 필요한 명령 모음. 진입점에서 읽을 조건을 명시한다.
- **자동 검사**: 구조·exports·생성 결과처럼 결정적으로 판정할 수 있는 제약. 해당 경계에서 실행되도록 하되, 구현 전에 알아야 할 위험 경고까지 검사로 대체하지 않는다.
- **Fleet Wiki**: Wiki가 소유하는 지식과 지침은 그 스코프의 승인·생성 계약을 따른다. 일반 Markdown처럼 압축하거나 우회 편집하지 않는다.

항목을 옮기기 전에 기존 소유 문서나 검사가 있는지 확인한다. 없어진 절차를 여러 문서에 복제하는 대신 하나의 도착지와 조건부 참조를 둔다. 짧다는 이유만으로 중요한 제약을 삭제하지 않으며, 모든 파일을 바꾸는 것을 전면 점검의 성과로 삼지 않는다.

## 개편 검증

지침 개편은 다음 두 층을 구분해 평가한다.

1. **정적 검증**: 이전/이후의 루트와 적용되는 하위 지침을 함께 읽는다. 참조 경로·스킬이 존재하는지, 소유권과 승인 경계가 충돌하지 않는지, 이관한 제약의 도착지가 있는지 확인한다. Wiki-governed 지침과 compiler-owned 출력은 별도로 확인한다.
2. **대표 작업 평가**: 같은 작업 프롬프트·모델·도구·검색 조건에서 이전/이후 지침을 각각 적용하고, 경로 선택·조건부 참조·권한 판단·검증 범위·종료 조건이 달라지는지 비교한다. 실제 실행이 없는 문서상 시나리오 점검을 행동 성능 검증으로 보고하지 않는다.

대표 작업은 변경한 지침의 경계에서 고른다. 예를 들어 Console의 시각 변경, core 패키지의 exports 변경, Desktop의 인증서 신뢰 변경, 문서 전용 수정, 승인된 구현 중 발생한 자체 회귀, 게시 승인이 없는 로컬 구현 완료를 비교할 수 있다. 문맥 크기 감소만으로 성공을 판단하지 않고, 필요한 제약이 사라지거나 무관한 절차가 활성화되지 않는지를 본다.

실패·비용·소요 시간·로드된 문맥을 기록할 수 있을 때 함께 비교하되, 표본 수와 실행하지 않은 평가를 밝힌다. 모델이나 harness가 바뀌면 재평가할 수 있지만, 모든 일상 작업에서 이 감사를 다시 수행하지 않는다.
