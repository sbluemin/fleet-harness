# Gateway 구현 참조

Gateway 레이어·모델 카탈로그·request policy·provider adapter를 변경할 때 해당 절을 읽는다. 일반 패키지 작업의 필수 사전 읽기 목록은 아니다.

## Layer index

| Layer | Responsibility |
|---|---|
| `src/canonical/index.ts` | Direction-neutral request/event vocabulary the wire and every adapter speak |
| `src/downstream/wire/` | Inbound protocols, one folder per wire. `anthropic-messages/` holds `protocol.ts`/`passthrough.ts` (the only two modules upstream may borrow) and `inbound.ts` (the Messages⇄canonical translator) |
| `src/downstream/harness/` | One folder per client, plus `contract.ts`. `claude-code/` carries its request vocabulary (`context.ts`), its id grammar (`discovery.ts`), and its `profile.ts`; `grok-build/` carries its own dotless id grammar and profile. The Anthropic discovery envelope both render into is the wire's (`protocol.ts`), not either client's |
| `src/transport/` | Direction-unaware transport mechanics: SSE framing, token estimate, wire log, keepalive, credential file I/O |
| `src/router/` | The HTTP serving seam behind explicit host-injected dependencies. `router.ts` routes; `request-policy.ts` carries the request-shaping contract and its step implementations; `http.ts`/`passthrough.ts` are its response primitives |
| `src/upstream/<provider>/` | One folder per provider, each gateway provider declaring its own `request-policy.ts`. `anthropic/` is the native passthrough and declares none. OpenCode behavior is additionally split by wire under `src/upstream/opencode-go/{anthropic,responses,chat-completions}/` |
| `src/models.ts`, `models.json`, `benchmarks.json` | Model catalog, context windows, effort ladders, and third-party benchmark evidence — bare catalog vocabulary, no harness id grammar |
| `src/auth/` | Provider credentials the user supplies as API keys: the `<dataDir>/auth.json` durable store, its provider-id namespace, and the Anthropic-compatible key-validation probe |
| `src/settings/` | Which catalog models a user exposed and where that choice is stored: stored shape, catalog-checked validation, selection resolution, the opt-in `providerPriority` spend order, and the `<dataDir>/ai-gateway.json` durable store |
| src/quota/ | Provider-neutral quota vocabulary, window normalization, and the cached usage service; per-provider probes live beside each provider as src/upstream/<provider>/quota.ts |

## Routing doctrine

- `models.json` + `benchmarks.json` + `src/models.ts` are the single central catalog SSoT; never split them or move ownership. The catalog carries each vendor lineup's current generation only — a superseded generation leaves the catalog instead of aging in place.
- `capabilityClass` records the provider's own lineup positioning (`flagship`/`standard`/`light`) — the quality prior where no measured evidence exists: what the provider claims, never a measurement. Classify a new model in this order: a service-tier sibling inherits its base's class, linked by `providerModelId` where it reaches the base's own wire id and by `variantOf` where the provider gave the variant a wire id of its own (Cursor's `-fast`); otherwise the provider's naming grammar decides — top tier tokens (`max`, `pro`) and the current generation of an unsuffixed mainline are `flagship`, mid tokens (`plus`), superseded generations of a former flagship, and a speed-first house model the provider sells *beside* the top seats it also resells (Cursor's Composer) are `standard`, light tokens (`flash`, mini-class names like `luna`, and an unlinked `-fast`) are `light`. One vendor model carries one class across every provider that resells it — a class that differs by provider makes one of the two statements false. Resolve ambiguity downward (overclassing seats a light model in judgment work; underclassing merely costs one candidate) and leave routing aliases (`auto`) unclassed — validation enforces both.
- `benchmarks.json` records third-party measured quality evidence from a single source — CursorBench — joined to catalog entries only through an explicit `benchmarkKey`, never by id-string matching. The single source is deliberate policy: benchmark figures are harness-relative and never compare across sources, so a second source only blurs host judgment with incomparable numbers. A model CursorBench has not measured carries no benchmark entry at all — the `capabilityClass` prior alone guides host judgment there — and reintroducing a second source is a user-authorization decision, not an authoring one. Where figures exist they outrank the `capabilityClass` claim. Validation enforces the join invariants; authoring and figure-update rules live with the schema in `src/models.ts`.
- Provider behavior belongs to `src/upstream/<provider>/`, and OpenCode's wire-specific behavior additionally to its wire subfolder. Which client the gateway is serving belongs to `src/downstream/harness/<client>/`; the protocol that client speaks belongs to `src/downstream/wire/<wire>/`.
- `src/router/` is the sanctioned serving seam and the only layer that may import both directions: it may import harness profiles and provider folders for dispatch, receives every host concern (settings reader, credentials, originator, model override, diagnostics sink, fetch) as explicit dependencies, and carries no host identity, no environment lookups, and no host lifecycle of its own.
- Which shaping a caller request receives before it reaches a provider is that provider's declaration, never the router's branch. `router.ts` routes — body, model, exposure, credential, gateway construction, dispatch, error mapping — and holds no per-provider request condition. `src/router/request-policy.ts` owns the `GatewayRequestPolicy` contract and every step's implementation; each `src/upstream/<provider>/request-policy.ts` states which steps its wire deserves and why. A provider without a policy fails to compile rather than inheriting another provider's answer, and the direction-boundaries test pins both that file's presence and its shape.
- The step implementations stay with the seam because they read Claude Code's own request vocabulary from `src/downstream/harness/claude-code/context.ts`, which no provider folder may import. So the one dependency pointing back at the seam is a provider naming the contract it implements, and it is `import type` only — the edge is erased at runtime and the seam still owns every real module. Any other upstream import of `src/router/` is a violation.
- A provider policy shapes the catalog, and a rewrite of what the client wrote is placed by who must receive it. A rewrite that has to cover the native Anthropic requests no policy sees belongs above the policies, unconditional in `router.ts` — the usage-limit directive strip is the one such step. A rewrite that must **not** reach the passthrough belongs in the policies instead, because that is the only seam native traffic never enters — the client identity/billing strip is the one such step, and it is declared by all six providers rather than centralized so that a provider added later states its own answer. Measure before adding a second: Claude Code attaches its shell-first directive on the Opus coordinate alone and never on a request that names a gateway model, so a gateway target and that paragraph do not co-occur outside the `FLEET_AI_GATEWAY_MODEL` override, and a stripper written for it was measured inert and removed.
- `src/downstream/wire/` must not import `src/downstream/harness/`. The wire serves every client that speaks it; an id grammar, a context coordinate, or a retry ladder reaching in there is what makes the package single-client. A client-specific value arrives as an injected function on the call options (`findModel`, `projectInputTokens`, `retryableStatus`) and its implementation stays in that client's folder. Absent means the neutral answer — no projection, no status lift — never Claude Code's.
- A client fact is a `GatewayHarnessProfile` field (`src/downstream/harness/contract.ts`), never a branch in `router.ts`: probe paths, credential shape, model id grammar, discovery payload, unconditional request sanitation, usage projection, and retry-status mapping. `deps.harness` absent is Claude Code, so a host that names no client keeps today's behaviour. Adding a client means adding a profile, not editing the router.
- Which harness serves a request is a **declared path segment**, never a judgment about the caller. `deps.harnesses` keys are selector segments, matched as the segment immediately preceding the wire endpoint suffix (`/ai-gateway/grok/v1/messages` → `grok`); an unknown or absent segment falls to `deps.harness`. Header sniffing — user-agent, credential shape, request fields — is forbidden here: it puts the client condition the profile seam removed back into `router.ts`, and it silently mis-serves any client that resembles another. The client writes its own base URL, so the segment costs it nothing.
- Provider-specific dispatch glue — code that builds an inbound translator or calls the router's passthrough for one provider — belongs to `src/router/`, not to that provider's folder (`router/opencode-dispatch.ts`). The provider owns its header and body policy; the router owns which path a turn takes.
- Same wire protocol is not a reason to share provider request/response/tool/header/capability semantics — duplicate provider semantics deliberately.
- Only canonical protocol vocabulary (`src/canonical/`), direction-unaware transport mechanics (`src/transport/`), and exactly two inbound-wire modules — `src/downstream/wire/anthropic-messages/protocol.ts` and `.../passthrough.ts` — may be shared across providers. Those two are borrowed only by the providers whose upstream wire IS the downstream wire (Kimi, OpenCode Go's Anthropic models), which relay a caller request without translating it. `src/transport/` must not import either direction, and `src/upstream/anthropic/native.ts` is Anthropic-owned provider semantics other providers must not import.
- Provider request/response/tool/header/capability exceptions cannot live in `canonical/`, `transport/`, or the root facade.
- `src/settings/` is a catalog reader, never a provider: it may consume `src/models.ts` and the Claude compatibility seam, but must not import a provider folder or carry provider request/response semantics. Hosts wire it with an explicit data root and an optional legacy directory; the package resolves no host path of its own.
- `src/auth/` owns where a user-supplied provider key is stored and how such a key is checked, and nothing else. Like `src/settings/` it is provider-neutral — it must not import a provider folder, and a provider's own coordinates (its store id, base URL, validation model) stay with that provider. It is also the one place in this package that may construct a credential store: provider folders and quota collectors still receive an `AuthService` explicitly, so no probe can reach a global credential file on its own. `auth.json`'s name and its stored provider-id strings are the user's signed-in state — changing either signs the user out silently, so both are frozen regardless of which package holds the code. Subscription credentials that a vendor CLI owns are not this: those files stay read-only reads in `src/upstream/<provider>/credentials.ts`.
- `src/index.ts` is a compatibility facade only: it re-exports the public surface from the new locations and must not add provider branching or behavior.
- The one sanctioned downstream→upstream coupling is `AnthropicMessagesGateway`'s backwards-compatible default constructor (`src/downstream/wire/anthropic-messages/inbound.ts` → `upstream/codex/responses/adapter.ts`, the legacy `OpenAIResponsesAdapter`). It is pinned by the direction-boundaries test; any other downstream import of an upstream folder is a violation.

## Constraints

- Keep Fleet orchestration and persona semantics out of this package; it knows providers, not Fleet personas.
- Provider usage/quota probing lives beside each provider (src/upstream/<provider>/quota.ts) with shared window vocabulary and caching in src/quota/; collectors receive their credential and auth dependencies explicitly — a collector never constructs the credential store itself.
- Each provider Responses implementation that applies strict mode rewrites every compatible tool schema into strict mode and strips the resulting nulls back out on the way in. **These two are one mechanism per implementation.** Change either alone and arguments silently gain or lose meaning: a surviving null reads as a real value to the client, and an un-rewritten schema loses the omission guarantee. The rewrite, the null stripping, and the argument-delta dropping below stay local to each such implementation — never centralize or import this semantic logic across providers.
- Strict compatibility is decided by an allowlist of JSON Schema keywords, never a denylist. The costs are asymmetric — judging a tool incompatible costs that one tool its guarantee, while wrongly admitting one returns a 400 that fails the entire request, every other tool included. Widen the allowlist only against an observed acceptance.
- Each provider Responses implementation that applies strict mode drops `response.function_call_arguments.delta` deliberately. Nulls cannot be stripped from a partial JSON fragment, so forwarding fragments would let the client reassemble un-stripped arguments. Restoring argument streaming reintroduces the defect.
- Strict mode makes omission expressible; it does not stop a model from filling an argument. Models still send the default quoted in a property's own description, and stating the omission rule in that description was measured to change nothing. Do not re-attempt schema-side persuasion — treat leftover default-valued arguments as accepted, since suppressing them cannot be distinguished from a caller who meant the default.
- The Cursor path has no equivalent guarantee. Its optional-argument pollution is known and unaddressed; do not assume parity between adapters.
- Cursor's redirect targets and its withheld catalog entries are two predicates, deliberately not one. A native exec may be translated into any redirect target, while only a tool whose capability Cursor owns outright — its shell — is kept out of the advertised catalog, because advertising both spellings of one capability invites the model to pick at random. `Grep` is a redirect target that is **not** withheld: the translation carries only the subset of that schema the native shape can express and fail-closes on the rest, so the caller's own tool is the better route and the redirect remains the fallback for a native call the model makes anyway. Collapsing the two back into one predicate either kills a redirect or hides a tool that had no duplicate.
- The Cursor Run gates on its HTTP response status before any body byte is read as Connect framing, and fails a transport end that decoded no frame. **These two are one guarantee.** A rejected Run's body is not Connect framing, so decoding it produces neither a frame nor an error; drop either half and an upstream rejection completes as a successful, empty assistant turn instead.
- Every Cursor model runs client tool calls over the live Run bridge — Auto, Composer, and Grok included. Measured: each of them suspends our client tools and continues from their results exactly as the named models do, and the exclusion they used to carry was hiding a correlation defect, not a provider difference. Re-excluding a model puts a cold dial and a full conversation re-upload on every one of its tool calls, so it takes a measurement, never a precaution.
- Cursor keeps writing a turn after the gateway has sealed it, and the park gate plus the three shapes that arrive late — the sealed turn's own tail, the echo of a call the client already answered, and a call the model raced past the seal — are **one mechanism**. The tail and the echo are tolerated where they are recognized, the raced call is deferred and replayed into the next segment, and everything else still discards the Run. Tighten one alone and a warm bridge dies one frame after every park; loosen one alone and the client is handed a call it never ran, or a turn never ends because an unsuspended item holds the finish gate open forever. Which frame belongs to which shape lives with the classifiers in `src/upstream/cursor/native/adapter.ts`.
- The OpenCode Chat Completions implementation gets its schema guarantee inbound, never outbound: that wire accepts `strict: true` and ignores it, so it prunes undeclared keys from completed tool-call arguments and rewrites no schema. Do not re-attempt an outbound rewrite there. Like the image-input policy the pruning binds to the provider instance and must never widen the public generic Chat Completions class, and it drops only *undeclared* keys — suppressing a declared argument stays forbidden by the strict-mode rule above. Which schemas it will and will not prune, and the measurement behind the rule, belong with the walker in `src/upstream/opencode-go/chat-completions/adapter.ts`.
- `FLEET_GATEWAY_WIRE_LOG` names the default file target for the inbound tool catalog, the canonical and provider wire bodies, and every response event as unlimited-append JSONL. An explicit in-process override takes precedence over the environment target; only override targets with `maxBytes` rotate at that limit and retain one `.1` backup. This log is the only way to see the argument JSON a model actually produced — provider behaviour differences are not otherwise observable from either side of this package.
